# @1outres/dsh-bot-core

Host-only plugin (row id `bot-core`) that registers the `bot` Cordis service. Other packages in this repository import its types from `@1outres/dsh-bot-core` and declare `inject = ["bot"]`, so they stay inactive until this row is loaded.

## Bot templates

A bot's Agent preset is composed from a template plus the bot's own overlay. Declare a template from any Cordis patch with the `@1outres/dsh-bot-core/template` row; it registers while the row is active and mounts nothing itself. Every row needs an `id`, and `!!js` nodes inside `plugins` are kept and evaluate when a bot's preset mounts. (Only there: `!!js` at the top level of the row's config, e.g. in `hostTools`, is not evaluated.)

```yaml
- insert:
    - id: bot-template-helper
      name: "@1outres/dsh-bot-core/template"
      config:
        id: helper
        name: Helper
        plugins:
          - id: persona
            name: "@deepseek-ai/dsh-persona"
            config:
              prefix: You are a helpful bot.
        hostTools: []
```

Like `@deepseek-ai/dsh-agent-preset`, the template row marks itself as a Loader group so its child rows stay unevaluated. `dsh --dump-config-schema` reports such rows as an "unrecognized Loader tree carrier"; the shipped preset rows get the same diagnostic, and it does not affect loading.

## Bot presets

Each bot runs under its own Agent preset, `bot-<botId>`, composed from its template (`default` unless chosen) and its overlay, inside the bot's execution environment (below). bot-core registers it once that environment is ready for the bot, re-registers it when the bot's overlay or template changes, and removes it with the bot. A rename does not re-mount it: the preset's display name ("Bot: <name>") keeps the old name until the preset is next registered (an overlay or template change, or a restart). Other plugins work through the `bot` service:

- `registerTemplate` / `templates` — the template catalog (the row above uses it).
- `previewPreset(botId, { template?, overlay? })` — what a change would compose to, without storing it.
- `configurePreset(botId, { template?, overlay? })` — merged with the stored record and validated in the write queue; nothing is stored when it does not compose.
- `presetOf(botId)` — `ready: true`, or `ready: false` with the `problem` (`pending: true` while it is expected to clear by itself, such as a template row that has not mounted yet). `watchBotPresets(ctx, listener)` (or `onPresetChange`, whose unsubscriber the caller owns) reports changes.
- `createSession(botId, { title? })` — starts a bot session under its preset, in the environment's `workspace` (below), and records it as the bot's; rejects while the preset is not ready. bot-core's own UI (a bot's **New session**) uses it too. A new session stays blank until someone writes into it, which the browser allows once its environment answers ("Blank sessions" below).
- `registerEnvironment` / `environment()` — the bot environment (below).
- `models` / `configureModels` / `modelCatalog` / `resolveModel` / `onModelsChange` — the bot's model roles (below).

## Bot models

Each bot has a model per role (`src/shared/models.ts`, `BOT_MODEL_ROLES`): `main` (its Main session and every session `createSession` starts), `utility` (a light model for formatting; stored only, no consumer yet) and `delegates` (the models a session the bot starts may run, a list; stored only). A choice is `{ kind: "profile-default" }` (DSH's `agentDefaultModel`) or `{ kind: "fixed", provider, model, reasoningEffort? }`. The spec is `docs/specs/bot-models.md` (repository root).

- **Storage.** `dsh_bot_models` (version 1, `host/models/domain.ts`), table `models` keyed by bot id, written only by `host/models/store.ts` (design rule 51). A new bot's row is written right after its record (`bots.create({ …, models? })`, roles not given start at `DEFAULT_BOT_MODELS`: both profile-default, no delegates). At start-up every bot without a row gets `DEFAULT_BOT_MODELS` and a row missing a role gets that role's default; readers throw on a missing row or role (the start-up completion is the only one). A deleted bot's row goes.
- **Checks** (`host/models/catalog.ts`), as DSH's model picker and `session.selectModel` check: the provider is in `llm.listProviders()`, the model in `llm.listModels(provider)`, the effort in `resolveModelInfo(…).reasoning.efforts`, then `llm.resolveCallConfig`. A fixed choice is checked when it is stored (nothing is stored when one is refused) and when it is used. Refusals: `bot-models/not-found`, `unknown-provider`, `unknown-model`, `invalid-effort`, `catalog-failed`, `rejected` (details `{ role, index? }`), `gateway/bad-request`. `llm` is a required inject.
- **Sessions.** `createSession` resolves `main` in the bot's realizer turn. A fixed model is passed as the Agent's options and recorded on the session in setup (`agent.model.select`, a `model/selection` event), so resumes keep it; one DSH cannot run refuses the session (no fallback). `profile-default` gets DSH's default as live accessors, as DSH's own sessions do (it follows DSH's default until the session's first request).
- **Live sessions** (`host/models/main.ts`). A change naming `main` is stored with `mainPending` and recorded on the Main session (`agent.model.select`, effective from its next step) at once when its Agent is live, otherwise when its Agent is next created or resumed; once applied, a model picked later in DSH's own picker stays. `profile-default` applies DSH's default of that moment. A route DSH cannot run then is warned about and stays pending. Other live sessions keep their model; `utility` and `delegates` changes are stored only.
- **Web UI** (`client/models/`, `client/settings/ModelsSection.tsx`; spec §9). The bot's settings have a **Models** section after General: rows Main and Utility (a searchable model picker, DSH's default first and named after the model it is now, then the catalog's models under their provider; an effort select when the model offers efforts) and a Delegates list (effort, move up / down, remove, Add model), every change saved as it is picked through `configureModels`. The catalog is read each time the page opens; a stored route it does not list stays as it is, marked Unavailable; `mainPending` is a quiet Pending pill on Main; `bot-models/*` refusals are worded per code on the row that caused them. The New bot dialog has a Model row for `main` (DSH's default unless another is picked). On a bot session DSH's composer model seat is empty (see Composer seats under Bot session shell); `/model` still works there (no way to hide a command).
- **`bots` Remote:** `models(id)`, `watchModels(id)` (stream), `configureModels(id, change)`, `modelCatalog()` (`{ profileDefault, providers, failures }`). There is no settings UI yet.

## Bot environment

Bots run only inside an execution environment (`BotEnvironment`, e.g. one VM per bot) that another plugin registers with `registerEnvironment`. At most one is registered at a time, and only the id the `environment` config names (default `incus-vm`), with an absolute, normalized `workspace`; `environment()` returns its id, isolated services and workspace. Without one, no bot preset is registered (fail closed), `presetOf` reports `pending`, and bot-core warns once after 30 seconds.

- **Sessions.** Every bot session runs in the environment's `workspace` (e.g. `/home/bot/workspace`, the same path in every bot's VM). bot-core never uses a Host path for a bot (the session's directory is the one inside the environment): bot-core creates the session's Agent itself (`agents.create`, with the session controller's own setup: model selection and `agentPresets.mount`; the model is the bot's `main` role, "Bot models" above), because DSH's `sessionController.create` makes the directory on the Host first. Bot sessions belong to no DSH Workspace (a Workspace is a Host directory); bot-core records which bot each session belongs to in its own storage (the `sessions` table), and the browser builds the Bots tree from that (newest first; a session DSH's title projection has not named yet shows as "New session N", N its place among the bot's other sessions in creation order, archived ones counted, so the number never changes whatever the listing order) and hides the bot sessions from the stock lists (where they would show as Ungrouped; the Ungrouped heading and its "show more" button go too while no other session is ungrouped in the browser's default view, i.e. not counting archived ones; with "show archived" on, an Ungrouped bucket of only archived sessions shows its rows without the heading). A session forked from a bot session in the Web UI is recorded as the bot's too. An Agent bot-core created belongs to bot-core's context, as one the session controller creates belongs to the session controller's: unloading bot-core ends it, and the session resumes on its next use.
- **Working directory.** DSH's Host `workingDirectory` service checks every Agent's directory with the Host's file system (on every turn, for subagents, the terminal…). For an Agent of a bot's session, bot-core answers its `working-directory/access` waterfall itself, without calling `next()`: the directory is checked with the environment's file system (the `fs` inside the Agent's composition, or its parent's for a subagent not composed yet), and a change is committed the way DSH does. A directory that does not exist in the environment (a session from before this layout, in a Host path) is switched once to the environment's workspace, with DSH's notice. If the environment cannot answer (a stopped VM), the recorded directory is kept and the bot's tools fail on their own. Every other Agent goes straight to `next()`, so Workspace sessions are checked by DSH as before.

- **Composition.** A bot's preset is one `cordis:group` row `bot-environment` that holds the environment's `rows(target)` first, then bot-core's own rows (`env-bot-core-files`, `env-bot-core-channel`, `env-bot-core-connectors`, `env-bot-core-schedule`, `env-bot-core-sessions`, `env-bot-core-prompt`, `env-bot-core-notes`, the group's own `@deepseek-ai/dsh-skill` `env-bot-core-skill` and `env-bot-core-skills`, "Skills" below, `env-bot-core-conversations`, "Past conversations" below, then the group's own `@deepseek-ai/dsh-web` `env-bot-core-web` and `env-bot-core-web-bridge`, below, and DSH's `present` as `env-bot-core-present`, "Sending files"), then the composed template and overlay rows. It isolates the environment's `isolate` services and always `ssh`, `fs`, `subprocess`, `shell`, `sandbox`, `sandboxPolicy`, `terminals`, `webTerminals`, `ptcRuntime`, `workflowEngine`, `worktrees`, `officeKit`, `computerUse`, `cuaAccess`, `web` and `skills`: inside the group they are the environment's or not provided, so a row needing one the environment lacks stays pending instead of reaching the Host's. The preset revision changes with the environment's rows and isolate list. A composition is never registered outside that group.
- **Refused in templates and overlays** (in every nested row: the Loader mounts a `cordis:group` row's children whatever its `group` flag says, so such a row must set `group: true`, and only `cordis:group` rows may; row ids are unique across the whole tree). The bot's preset reports the problem, `configurePreset` stores nothing, `previewPreset` returns it:
  - the row id `bot-environment` and ids starting with `env-`;
  - paths, URLs and Loader builtins other than `cordis:group` (`cordis:include`…), and other row carriers (`@deepseek-ai/cordis-plugin-group`, `cordis-plugin-include`, `cordis-plugin-loader`, `dsh-agent-preset`, `@1outres/dsh-bot-core`);
  - packages that run on the Host or assume a Host path (subpaths included): `dsh-fs-local`, `dsh-fs-sandbox`, `dsh-subprocess-local`, `dsh-sandbox-local`, `dsh-bash-local`, `dsh-bash-sandbox`, `dsh-ssh`, `dsh-fs-ssh`, `dsh-subprocess-ssh`, `dsh-sandbox-ssh`, `dsh-sandbox-policy`, `dsh-ptc-runtime-node`, `dsh-tool-executor-ptc`, `dsh-workflow-ptc`, `dsh-tool-workflow`, `dsh-tool-office`, `dsh-office-kit`, `dsh-tool-working-directory`, `dsh-working-directory`, `dsh-tool-terminal`, `dsh-tool-bash-persistent`, `dsh-mcp-client`, `dsh-mcp-manager`, `dsh-tool-cordis`, `dsh-tool-session-query` (it authorizes by equal working directories, and every bot shares one), `dsh-tool-schedule` and `dsh-schedule` (they start sessions through `sessionController.create`), `dsh-tool-workspace-dependencies`, `dsh-host-open-in-app`, `dsh-creation-recommendations`, `dsh-experimental-liveshare`, `dsh-native-command`, anything starting with `dsh-pwsh-`, `dsh-tool-pwsh`, `dsh-terminal`, `dsh-plugin-manager`, `dsh-cua`, `dsh-computer-use`, `dsh-experimental-…worktree…` (all `@deepseek-ai/`), and `@1outres/dsh-bot-vm`;
  - packages that provide a web seam or web providers, which would bypass bot-core's web settings and secrets ("Web lookup", below): `@deepseek-ai/dsh-web`, `dsh-web-fetch-http`, `dsh-web-deepseek-api`, `dsh-web-search-deepseek`, `@1outres/dsh-plugin-exa` and `@1outres/dsh-bot-web`;
  - packages that provide skills, whose skills would not be the bot's `skills/` ("Skills", below): `@deepseek-ai/dsh-skill`, `dsh-skill-filesystem` and `dsh-skill-office`;
  - `isolate` values other than `true` (`false` would un-isolate, a label joins a realm shared across the Host), and an `isolate` or `intercept` of a service the group isolates;
  - `@deepseek-ai/dsh-tool-present` (subpaths included), which bot-core puts in every bot's group itself (`env-bot-core-present`, "Sending files" below), and `present` in `hostTools` (the Host's reads Host paths);
  - `hostTools` not listed in the `allowedHostTools` config (default none).
- **Overlays only** may not set Host-path config of otherwise allowed plugins: `dshHome`, `agentsHome` of `dsh-agent-instructions`.
- **Readiness.** Registering the environment `ensure`s every bot; a bot created later is ensured when it is stored. The preset is registered once `ensure` resolved (`pending` meanwhile). A rejected `ensure` makes the preset not ready with the reason (warned once per reason) and is retried after 5 s, doubling up to 5 min. The environment's `onChange(botId)` re-runs `ensure` (the bot stays ready unless it fails). Unregistering the environment unregisters every bot preset; unloading bot-core aborts running `ensure`s and keeps the environments. A scheduled resume of a bot session waits only 15 seconds after start-up (below): if the environments take longer to come up, that resume fails.
- **Lifecycle.** Creating a bot is refused while no environment is registered. Otherwise bot-core stores the bot unlisted and waits (up to 10 minutes, outside the write queue, through failed `ensure`s being retried) until its environment is prepared and its preset registered; then it starts the Main session and greets as before. Every new session (`createSession`: a Main, a New session, one for another plugin) is prepared first: a check through the session's own file system must reach the bot's workspace (every 3 s, for up to 3 minutes; then it goes on anyway, with a warning), because a turn whose preparation cannot reach the environment fails and consumes its message, which happened to the first turn on a VM that had just booted. A new bot's greeting is sent once its Main is prepared. The browser's create dialog stays busy meanwhile and cannot be closed (a creation cannot be cancelled), and the `bots` Remote reports the sessions of bots being created, so the browser hides them as it hides the listed bots'. If that does not happen in time (or the environment goes away, or bot-core unloads), the bot is not kept: its record goes, any session it started is archived, and its environment is removed. Deleting a bot archives its sessions, unregisters its preset, then calls `remove(botId)`, retried with backoff (with no environment registered, by the next one, in memory only; the provider may clean up environments of unknown bots). What happens to the workspace's files is the environment's choice: `incus-vm` (`@1outres/dsh-bot-vm`) deletes the VM but **keeps the files on the Host** in `~/.dsh/bots/<id>/workspace` (its `hostRoot`), where they were all along; the delete dialog says so, and removing that folder is up to the user. A stored bot without a Main gets one when its preset becomes ready.
- **Bots from before this layout** (storage version 1) had a Host directory (`~/.dsh/bots/<id>`) registered as a Workspace. At start-up bot-core records that Workspace's sessions as the bot's and deletes the Workspace registration (the Host directory itself is left alone; remove it by hand. Its path, `~/.dsh/bots/<id>`, is also where `@1outres/dsh-bot-vm` keeps a bot's `workspace` now; an old one is an empty directory and does no harm). Their sessions keep their old `cwd` in the header and are moved to the environment's workspace on their next turn (above). The storage domain is now version 2 (it still reads version 1); an older bot-core refuses it.
- **Known limits.** Host features that read a session's directory with the Host's file system find nothing for a bot session (the bot file viewer, below, replaces the Files sidebar and file previews): @-mentions of files in the composer, changed files (DSH may log a warning per turn), and the Web terminal (bot sessions cannot open it). Attachments other than images that a person adds in the Web UI's composer are passed as Host paths, which the VM cannot read (channel attachments go to the inbox instead, above). A new file written by the bot's `write` tool is mode 0600 inside the VM: dsh-fs-local's atomic write stages it with 0600 and keeps that mode for new files (an existing file keeps its mode), the same as on the Host; `bash` creates files with the VM's umask. A schedule a user creates for a bot session with a `new` or `new_once` target fails at delivery: DSH creates the new session through the session controller, which makes its directory (`/home/bot/workspace`) on the Host first and gets `EACCES` (`/home` is root's); a `this_session` target only resumes the session and works. **Never create `/home/bot` on the Host**: its absence is an extra fail-closed guard, since any Host feature that checks a bot session's directory with the Host's file system (a bot session resumed while bot-core is not loaded, a resumed subagent of a bot that had named a non-bot preset, a stock session creation in that path) fails there instead of running in a Host directory of that name.

A preset that cannot be realized (missing template, an overlay that no longer applies, a registration the Agent preset registry reports broken) is unregistered rather than left at its old composition, so the bot's sessions do not resume on settings that no longer hold; they resume once it is fixed. A missing template is reported only if it stays missing for 10 seconds. A due schedule that resumes a bot session within 15 seconds of start-up waits (within that window, never past an unload) for the bot's preset; DSH delivers all due tasks in one queue, so the window is shared, not per session.

A template or overlay may not let subagents pick another preset (`agentPreset` / `allowedAgentPresets` naming anything but the bot's own preset); such a composition is refused.

### Trust boundary

The profile is trusted, an overlay is not. Templates (declared in the profile with the template row) may use Loader `!!js` and any plugin package the bot environment rules above allow. An overlay given to `configurePreset` / `previewPreset` may come from a chat message or the browser, and the Loader imports a row's `name` and evaluates `!!js` on the Host, so an overlay:

- may not carry `!!js` expressions;
- may only name plugins that a registered template uses, plugins listed in bot-core's `allowedPlugins` config, or `cordis:group` (nested group rows are checked too);
- may never name a path, a URL (`file:`, `data:`, …) or a Loader row that reads other entries (`cordis:include`, `@deepseek-ai/cordis-plugin-include`, `@deepseek-ai/cordis-plugin-loader`), even when listed.

Stored overlays passed these checks when they were configured and are not re-checked against the allow list.

## Web lookup

Every bot's `web_search` and `web_fetch` (the template's `tool-web` row) go through a **web backend** bot-core chooses, never through the Host's `web` service, its settings page, providers, `DSH_WEB_*` or keys. The spec is `docs/specs/bot-web.md` (repository root).

- **Backends** (`src/web-contract.ts`, re-exported from the package entry). A plugin registers one with `registerWebBackend` (`@1outres/dsh-bot-web` registers Exa): an id, a name and description, its secret fields, a `search` and/or `fetch` operation (`placement: "host"` for now; `run(request, { botId, secrets, signal })`, failures thrown as `WebError`) and `test` (one request with the secrets: `ok`, or `invalid-secret`, `no-credits`, `rate-limited`, `unreachable`, `unexpected`). The descriptor is checked (`host/web/catalog.ts`). `webBackends()`, `webStatus()` and `onWebChange` read the state.
- **Settings**, shared by every bot: the storage domain `dsh_bot_web` (version 1, `host/web/domain.ts`), table `settings`, one row `global` (`{ backend, search, fetch }`), written only by `host/web/store.ts` (design rule 44). A first start stores `DEFAULT_WEB_SETTINGS` (Exa, both on). **Secrets**: one credential record per backend, `bot-core/web-<backend>` (a `grant`, payload `{ version: 1, secrets }`, `host/web/vault.ts`); the browser only learns whether each is set. A backend that goes away keeps its record. Without DSH's `credentials` service every capability is unavailable.
- **Status** (`host/web/status.ts`, pure), per capability, in this order: `disabled`, `unavailable` (`not-registered`, `no-capability`, `no-credentials-service`), `missing-secrets` (which keys), `ready`.
- **Composition.** Every bot's group isolates `web` and holds `env-bot-core-web` (`@deepseek-ai/dsh-web` with `searchProvider` and `fetchProvider` fixed to `bot-core`) and `env-bot-core-web-bridge` (`@1outres/dsh-bot-core/web`, sealed with the revision token like bot-core's other rows), which registers the `bot-core` provider for each capability the backend has (design rule 45). Every `tool-web` row (nested ones too) gets `search` / `fetch` = what the template asks (true when absent) and what the backend has. Only the backend and its capabilities are composition inputs: their change recomposes every bot.
- **When changes apply.** A live Agent keeps the preset revision it started with (DSH keeps it until the Agent ends; a Main lives until DSH restarts). So turning a capability on or off does not recompose: the bridge's `ready()` and calls use the settings read at the calling Agent's `turn/start` (`agents.currentInitiator()`) for that whole turn, so both directions apply from every bot's next turn, the live Main's included, and never inside a running turn. A key that is set, replaced or removed applies from the next step (`ready()` reads the record; tool-web asks it every step), without recomposing. **Known limit:** a backend registered or unregistered later (or gaining a capability) reaches live Agents only once they are created again (a restart); new sessions get it at once. The bridge accepts every revision token bot-core registered during this load, since live Agents keep using their revision's bridge.
- **Readiness and calls** (`host/web/bridge.ts`). `available()` is always true; `ready()` is true while the capability is on for that turn, the settings' backend is registered with it, and every secret is stored (no network). Until the key is set, `web_search` / `web_fetch` do not show at all; nothing falls back to the Host's web or another backend. A call that reaches the bridge anyway is refused with `WEB_PROVIDER_UNAVAILABLE` or `WEB_PROVIDER_CREDENTIAL_MISSING`.
- **`botWeb` Remote** (`host/web/panel.ts`): `view()`, `watch()`, `setEnabled(capability, enabled)`, `setSecret(key, { op: "set", value } | { op: "clear" })` (trimmed, non-empty), `test()` (stored secrets, 15 s, one at a time). Refusals: `bot-web/unknown-secret`, `missing-secrets`, `not-registered`, `no-capability`, `busy`, `unavailable`, `gateway/bad-request`.
- **Web lookup section** of the dsh-bots settings (`client/web/`, registered in `client/wiring/web.ts`, first): a group titled with the backend holding its key as a `SecretRow` (Set / Not set, never its value; Set and Replace open the inline editor, Remove asks first; a typed, unsaved key asks before it is lost) with a row button **Test** while the key is stored (billed as one search; for a while its result — Valid, Rejected, No credits… with the backend's message as the tooltip — replaces the pill, `data-dshb-web-test-result`), and a group **Capabilities** with a `Switch` per capability (`data-dshb-web-switch`), saved at once and disabled without the key; a capability the backend cannot serve shows an Unavailable pill with the reason as its tooltip. No description or warning text is shown. Its badge is a warning while a capability that is on cannot be used; the Bots heading's dsh-bots settings button (a wrench, `data-dshb-global-settings-open`; the bot's own settings keep the gear) is marked (`data-dshb-global-settings-attention`) while any section of the dsh-bots settings has a warning or danger badge (`client/global-settings/attention.ts`).
- **Upgrading.** The first start stores the defaults; bots have no Exa key yet, so `web_search` and `web_fetch` disappear until one is set: open **dsh-bots settings → Web lookup** (the Bots heading's wrench is marked) and enter the bots' Exa API key. The Host's Exa key (`EXA_API_KEY`) is not copied. Every bot preset's revision changes once (the new rows). `allowedHostTools` could still grant the Host's `web_search` / `web_fetch`; do not, as they use the Host's web settings and network. Build `lib/web.js` (a full `pnpm build`) before DSH loads the new `lib/index.js`.
## Welcome guide and release notes

(`docs/specs/bot-onboarding.md`.) Every page shows them until one finishes them; the state is the Host's, followed through the `botOnboarding` Remote.

- **State** (`host/onboarding/`, storage domain `dsh_bot_onboarding` version 1, one row: the guide `open` / `creating` (its bot) / `done` (`created`, `later`, `existing`), and `notesSeen`, the newest dsh-bots version whose notes were read; written only by `host/onboarding/store.ts`, design rule 57). The first start decides once: stored bots, web lookup settings stored by an earlier start or a stored OAuth client make it an existing installation (guide done, every note up to now shown); otherwise the guide opens and no note is shown. A start whose versions since `notesSeen` have no note only records the new version.
- **Release notes** (`host/onboarding/source.ts`, `releases.ts`, `notes.ts`): the running version and the repository are bot-core's `package.json` `version` and `repository`. While the stored version is behind, the Host reads the repository's GitHub releases (`v<semver>` tags, not drafts, newest first) after it up to the running one, once per start; their English Markdown bodies are shown on every page until one page acknowledges them. Unreadable (offline, refused, rate-limited): nothing is shown or stored, and it reads again after 1 min, doubling up to 1 h. No release with a body in between: the version is only recorded. The notes are written in the release (`infra/RELEASING.md`), never in the code.

No ×, Escape or mask click closes it. A page that showed it opens the bot's Main when it is done (or shows its creation until the bot is listed). Then the release notes, a dialog of each release's Markdown (drawn by `client/markdown.ts`, never as HTML) with only **OK**.

## Bots section

The sidebar's **Bots** section (`client/BotsSection.tsx`, `BotGroup.tsx`, `BotSessionRow.tsx`, derived by `client/tree.ts`) sits above Workspaces, in the same viewport as the panel list (`[data-sidebar-scrollport]`, `client/placement.ts`). It has no height limit or scroller of its own: like the panel list, it scrolls away before Workspaces scrolls its own rows (DSH's sidebar hands the wheel over, and the Workspaces section is at most one viewport tall), so Workspaces stays reachable however long the bots get; Show more keeps each bot short. Only the fallback placement under New Session, outside that viewport, keeps a bounded scroller.

- **Tree.** One WAI-ARIA tree with a single tab stop, as Workspaces: ↑/↓/Home/End move, → expands a bot or enters it, ← collapses it or returns to the bot, Enter/Space activate. A bot row opens Main; expanded, it lists **Main** first (it is never archived and has no archive action), then the bot's other sessions **newest first**, then the overflow row. Expansion is kept per bot in `localStorage` (`dsh-bots:expanded`); a bot without one follows the selection.
- **Show more** (`client/session-window.ts`), the same rule as Workspaces' "Show more" (dsh-client-ui-workspace `SESSION_WATERMARK_BASE` / `SESSION_WATERMARK_AUTO_MAX`): a bot lists 5 sessions besides Main, and a last row "Show N more sessions" ("Show 1 more session") adds 5 more each time (all of them once 5 or fewer remain), then reads "Show less", which folds back. The window never hides the selected session (wherever it is: opening a session from anywhere reveals it) nor a running one within the first 50, and once raised it stays for the page; collapsing the bot folds it back. The overflow row is a treeitem: Enter or Space acts on it.
- **Archive.** Each session row but Main shows an Archive button on hover, and a right click, the menu key or Shift+F10 opens its menu (`ctx.contextMenus` target `bot-session`, `client/session-menu.ts`) with **Archive session**. Archiving goes through DSH's own `ctx.uiWorkspace.archiveSession`, as Workspaces' rows do (`client/session-archive.ts`): a session with running work is refused by the Host (`workspace/session-active`) and bot-core asks first, naming the work, then stops and archives (`stopActivity`); any other refusal shows on the bot's row. DSH clears the main view of an archived session; bot-core opens the bot's Main instead when the archived session was on screen (unless the user went elsewhere meanwhile). A notice then offers **Undo** and **Show archived**.
- **Archived sessions.** The bot's menu has **Show archived sessions** (only while the bot has an archived session) / **Hide archived sessions** (per bot, kept in `localStorage` as `dsh-bots:archived-shown`; showing them also expands the bot). Archived sessions then appear in place, newest first, grayed, under the same window, with an Unarchive button and an **Unarchive session** menu. As in DSH, an archived session cannot be opened (DSH clears an archived session from the main view): activating its row says so. Bot sessions stay hidden from the stock lists, archived or not, so DSH's own archived filter never lists them.

## Language and formats

The browser half's copy is `client/i18n.ts` (`en`, `ja`), registered with dsh-client-locale under the `dsh-bot-core` namespace; a DSH language bot-core has no dictionary for shows the English one (DSH's fallback chain).

- **One formatter** (`client/locale-format.ts`, `localeFormat(t)`). Dates and times (`instant(at, "dateTime" | "time")`: `Nov 23, 2026, 9:28 PM` / `2026/11/23 21:28`, or `9:28:18 PM` / `21:28:18`), relative times (`relative(at, now, "largestUnit" | "seconds")` with `Intl.RelativeTimeFormat`: `in 5 minutes` / `5 分後`) and counts (`count(key, n, params)`) go through it, and nothing else in `client/` formats them (design rule 47). Its language is the dictionary's own `format.locale` entry, read through the same `t`, so formats follow the language the surrounding text is actually in, and change with DSH's language setting without a reload.
- **Time zone.** Instants shown to a person (an approval's request, expiry and decision, a connector's next retry) are in the browser's time zone. A bot's `timezone` setting is for the bot's own schedules (Host-side), not for what the Web UI shows.
- **Plurals.** A message that depends on a count is a family of keys `<key>.one`, `<key>.other` (and any other CLDR category its languages use), picked with `Intl.PluralRules` of `format.locale`, with the number formatted for that language in `{count}`. Japanese words both the same. `PluralKey` is the type of such families; `test/locale-format.test.ts` checks that every dictionary words each category its language uses.

## Bot session shell

The browser half (`src/client/index.tsx`) only composes its parts from `client/wiring/`: stylesheets (`styles.ts`), session classification (`classification.ts`), the Bots section and its actions (`bots-face.ts`), archiving bot sessions with its confirmation and notices (`archive.ts`), dialogs (`dialogs.ts`), the file viewer (`files.ts`), the shell (`shell.ts`) and the right sidebar lockdown (`rightbar.ts`). State lives in React-free stores and models (`store.ts`, `session-classification.ts`, `slot-priority.ts`, `slot-registration.ts`, `menu.ts`, `session-menu.ts`, `session-archive.ts`, `session-window.ts`, `tree.ts`, `files/*-model.ts`, `sidebar/lockdown-status.ts`); components only draw them.

While the main view shows a bot's session, the browser replaces DSH's conversation shell with bot-core's (`client/shell/`): a header in DSH's conversation header measures (one 50 px row with a hairline: 24 px avatar, the bot's name, the session's name after a `/` when it differs, and a settings button that opens the bot's settings screen, below), the conversation on **Chat** only (no Chat / Trajectory / … tabs), and a vertical menu bar on the right whose first button sits on the header's centre line (Files, Notes, Actions, then the panels of the connectors the bot has on; a new session starts from the bot's row in the sidebar). At 640 px and below the menu bar folds into a menu button in the header (`data-dshb-shell-menu-button`, a dot while an entry waits). Bot-core adds nothing to the conversation column that shrinks the transcript: the bots list's state (reconnecting, unavailable), a failure of the bot's row actions (New session, Archive, Unarchive) and the session's notice (what the viewer could not open, or a refused right-sidebar lockdown, which outranks it until dismissed for the page) are banners floating under the header over the transcript (`data-dshb-shell-banners`; one look, tone by colour; a dismissible one ends in × and dismissing it moves focus to the bot's name). Every other session shows DSH's own shell, unchanged.

**Bot settings** (`client/settings/`). One large popover in `shell.overlay` (over a mask that closes it like ×) holds every setting of a bot: a one-line header (24px avatar, name, ×), a vertical tab list of sections on the left (↑/↓/Home/End move, Enter opens) and the open section's page on the right; on a window of 640px or less it is a full-screen sheet whose first page is the list of sections. A section may push one detail page (the frame draws the way back, named after the section). Escape leaves the detail page, then (on a sheet) the section, then the screen, and focus returns to where it was opened. It opens from the header's settings button and from the row menu (**Settings…**). Its state is one store, `{ botId, section, detail, nav } | null` (`settings/flow.ts`), opened with `openSettings(botId, section?, detail?)`, and closed by itself when the bot leaves the list. Sections are registered (`settings/sections.ts`: `register({ id, order, label, icon, component, badge? })`); the screen only draws them. A section receives `{ t, bot, page, close, confirm }` (`page`: the detail shown, `open(detail)`, `back()`): settings are saved as they change, an inline editor that holds typed text (`client/ui/` `TextField`, `SecretRow`, or `usePendingEdit`) makes any move or closing ask before the text is dropped, and the section may close the screen after an action that ends it or ask before a step with consequences. bot-core's sections: **General** (the name, saved on Enter or leaving the field; the avatar, with the same `AvatarPicker` as the New bot dialog, saved when picked; the time zone, a searchable list saved when picked; and a last row **Delete bot…**), **Models** (the model of each role, see Bot models), **Channels** (one group per channel plugin, every field saved on its own; the nav shows a dot only for an incomplete (amber) or failed (red) channel) and **Connectors** (a list, then a page per connector and per provider of accounts). **Delete bot…** and the row menu's **Delete…** open one confirmation over whatever is open (`client/DeleteBotDialog.tsx`, `client/bot-deletion.ts`, `BotsFace.confirmDelete(botId)`): Delete is enabled once the bot's name is typed, and the bot's settings close once `removeBot` resolves. An uploaded image is cropped to its centered square and scaled to 256 px, then re-encoded (PNG, then WebP and, without transparency, JPEG at falling quality, then smaller sizes) until it fits the avatar limit; an animated GIF keeps its first frame and says so, and a file that cannot be used names why.

**dsh-bots settings** (`client/global-settings/`). Settings shared by every bot live in a second screen of the same kind, separate from any bot's: it opens from the wrench button in the Bots section's header ("dsh-bots settings") and from bot-core's **dsh-bots** page in DSH's own settings (`settings.section`, registered only while DSH's settings shell declares it), which holds one row, **dsh-bots settings**, with **Open**: the button closes DSH's settings panel (the section's `close`) and then opens this screen, so the two never stack and focus lands in this screen. Its state is `{ section, detail, nav } | null` (`global-settings/flow.ts`); sections register like a bot's (`global-settings/sections.ts`, `register({ id, order, label, icon, component, badge? })`) but receive `{ t, page, close, confirm }`, nothing of a bot. While none is registered the screen says there are no settings yet. The two form a modal stack (`wiring/screens.ts`, `settings-frame/stack.ts`): opening this screen from a bot's (Connectors' **Open the dsh-bots settings**) opens it over the bot's, which stays as it was, out of reach, and is back once this one closes; opening a bot's screen closes this one first, asking about typed text. Both screens are the same frame (`client/settings-frame/`: `SettingsFrame` draws the header, the nav, the page and the confirmations; Escape, Tab and focus go through the layer stack of `client/ui/layers.ts`, which bot-core's dialogs share; `createSectionRegistry` and `createFrameFlow` hold the sections and the open screen's state); `settings/` and `global-settings/` only say what the screen is about and what a section receives.

**Shared components** (`client/ui/`). Every section and screen composes the same parts instead of its own markup: `Group` (an `h4` title over a hairline frame of rows), `Row` / `BlockRow` / `NavRow` / `LinkRow` / `AddRow` / `ButtonRow` (a row that is one action), `RowMenu` (a row's `…` menu), `PageTitle`, `Switch`, `Segmented`, `Select`, `SearchSelect`, `TextField` / `TextFieldRow` (saved on Enter or leaving the field), `TextArea` (a list, saved on leaving it), `TextInput` (the same look for a dialog's field that its form sends), `SecretRow`, `StatusPill`, `Button` (`primary`, `secondary`, `row`, `icon`; `tone: "danger"`; `expanded` / `controls` for a disclosure, `form` for a submit outside its form), `EmptyState`, `ErrorText`, `Tag`, `Code`; their look is `client/ui/styles.ts`, in DSH's measures and theme tokens. Opening a settings screen, the New bot dialog or the archive confirmation on a narrow window closes DSH's sidebar drawer first (`wiring/drawer.ts`, `ctx.layout.toggleSidebar()`).

- **How it is swapped.** `main.conversation` is a single Slot, where the lowest priority renders alone. bot-core registers its entry there (`client/slot-registration.ts`, wired in `client/wiring/shell.ts`) while the session `main.conversation` is bound to is a bot's or not classified yet, and disposes the registration for every other session, so DSH's ConversationRoot renders those. That session is read from the source the Slot renderer binds the scope with, dsh-client-ui-session's `ctx.uiSession.adapter.current` (`client/main-session.ts`). Two DSH rules force registering per session: an entry may `renderSlot` only the children its own registration declares, and `conversation.header` is already declared by ConversationRoot's entry (declaring it again throws), so no entry of ours could show the stock header for a non-bot session; and a single Slot refuses a second registration at an equal priority, while bundle client plugins call `ctx.slots.register` directly (only the `cordis` tool's dynamic packages get a priority assigned), so the priority is explicit (see Slot priorities) and tried once. A refusal (another plugin holds `main.conversation` at that same priority) is logged with `console.error`, is final until reload (no other priority is tried), and the Bots section shows it as an alert; bot sessions then show DSH's shell.
- **Slot priorities** (`client/slot-priority.ts`). Every seat bot-core takes over for bot sessions is registered at one priority, `BOT_SESSION_PRIORITY` (`Number.MIN_SAFE_INTEGER`, finite because SlotCore orders entries by subtracting priorities): `main.conversation` (the shell), `rightbar.session` (the lockdown), `conversation.input.model` and `conversation.input.permission` (the emptied composer seats) and the `conversation.composer` chain entry (the interaction card). A single Slot renders its lowest entry and a chain elects its lowest first; DSH's entries sit at 0, and a plugin that replaces one of these seats for every session sits below it (the `cordis` tool's packages at -1, -2, …, `@1outres/dsh-plugin-model-picker` at -100). bot-core's entries are only registered while the main view shows a bot session (or one not classified yet), and the interaction card only elects bot-core's own carriers, so taking the floor keeps those replacements off bot sessions and leaves them in force everywhere else. bot-core's other registrations add their own cells (list and hoc `id`s, keyed `key`s: the Bots section, dialogs, the settings page, the refused file tab, menu icons) and shadow nothing, so they keep the default priority.
- **Which sessions** (`client/session-classification.ts`). Once a bots list has arrived (also while it reconnects, on the last one), it decides: each bot's Main and other sessions, and those of bots being created, are bots'; everything else is stock. Until then the session list's summary decides from the session's agent preset (`projectionValues.agentPreset`): `bot-<id>` is a bot's (its bot not known yet: a pending header), another preset or the default is stock, and a session list not ready or a summary without the field leaves it **unknown**. An unknown session gets only a neutral placeholder ("Loading the session…": no header, no menu bar, no DSH shell), so a reload never flashes DSH's header on a bot session nor bot-core's on a Workspace session. The main view without a session is unknown too while DSH's session list or Workspace list is still pending (`client/main-session.ts`): ui-workspace restores the saved selection only once both are ready, synchronously for a bot session, so a reload never flashes DSH's start screen before a bot session is restored; once both lists have arrived, no session is DSH's own home (stock). The preset is provisional and wrong in two known cases, both corrected when the list arrives: a legacy Main (default preset, below) reads as stock, and a Workspace session where the user picked a bot's preset (locked down, see Isolation) reads as a bot's. Nothing about sessions is remembered in `localStorage`.
- **The bots list's state** (`client/store.ts`). `loading` until the first list; `ready`; `reconnecting` when the stream broke after a list arrived (the last list stays on screen, and the Bots section and the shell header say "Reconnecting to bots…"); a broken stream is reopened after a backoff (1 s, doubling to 30 s while no list arrives), or at once when DSH's connection establishes a new generation (`ctx.connection.generation`), so the notice clears as soon as the transport is back; `unavailable` when no list ever arrived; `failed` when the Remote could not be mounted. While unavailable or failed, a session classified as a bot's keeps the bot shell with an alert that bots are unavailable, never DSH's shell.
- **Content.** The shell renders DSH's `conversation.content` Factory as the main occurrence (`variant: 'main'`: document paste reaches its composer, the hero frame and the transcript width preference work as in DSH's shell), with its `views` position fixed to Chat (`renderSlot('conversation.session', { view: 'chat' })`, as DSH's embedded subagent chat) and a copy of DSH's width handles.
- **Blank sessions.** A bot session has no Workspace, so DSH's hero keeps the composer of a blank one inert ("Choose workspace"; dsh-client-ui-conversation `ConversationContent` disables it while `hero` is set and no Workspace holds the session). The shell therefore renders the `conversation.content` Factory of a blank bot session with `hero: false` and the `active` phase (`client/shell-phase.ts` `botShellView`; a session still replaying stays `settling`): the empty chat and the normal composer, ready for input, with no turn and no model call needed. Only while the session is being prepared (`BotsSnapshot.preparingSessionIds`, from `host/preparations.ts`: a new session until its environment answers, a new bot's Main until its greeting is sent) or while its bot is not listed yet, the shell shows "<bot> is getting ready…" instead. A New session and a new Main that replaced the former one then take input as they are, with no greeting.
- **Composer seats** (`client/wiring/composer-seats.ts`). DSH's composer model seat `conversation.input.model` (ui-model-selection's picker) and permission seat `conversation.input.permission` (ui-permission-presets' selector) are single Slots; while the main view shows a bot session (or one not classified yet) bot-core holds each at `BOT_SESSION_PRIORITY` with an entry that draws nothing, released for every other session, so a bot's model comes only from its settings and its permission is always `BOT_PERMISSION` (see Permission and prompt). Their priority is below that of DSH's controls (0) and of a plugin that replaces one everywhere (`@1outres/dsh-plugin-model-picker` holds the model seat at -100), so they render on bot sessions, and every other session keeps whichever control is in force. Each seat is registered on its own: a refusal (another plugin holds that seat at `BOT_SESSION_PRIORITY` itself) is final, leaves the other seat emptied, and is shown in the Bots section like the shell's. The `/model` and `/permission` commands stay (DSH's `commandUi` cannot hide a contribution per session).
- **Right sidebar.** DSH's right sidebar never shows on a bot session; its Files, Terminal and other tools are replaced by the bot file viewer (below).
- **Failures.** Everything the shell renders sits in its own error boundary: a failure logs to the console (naming DSH's `SlotAssemblyError` / `HocContentError` when that is what it caught) and blanks the screen with a short notice ("This session cannot be shown."); the next session starts fresh. It never falls back to DSH's shell for a bot session, which would bring back the title row, tabs and the right-sidebar opener. (Only an error outside that boundary, in the registration's `inject`, would make DSH's renderer retire the entry and show its own shell.)
- **Connector panels** (`client/connector-panels/`, wired in `client/wiring/connector-panels.ts`). Every registered connector with a `panel` that is not off for the bot gets a menu bar button after Files and Actions, with the glyph its `panel.icon` names (from the bot's `botConnectors.watch`, shared with its settings and reopened when it breaks), with a dot while its `status.request` is open. It opens the connector's panel in the shell's side panel frame (`client/shell/SidePanelFrame.tsx`, shared by Files, Actions and connectors; one side panel per session, `client/shell/side-panels.ts`: opening one closes the other; its width is kept per page, default 720 px). The frame shows the connector's readiness as an `EmptyState` with the connector's glyph (off with a button to its settings, waiting with the reason, preparing with the connector's `preparation.hint` as title and the stage as a compact row with the elapsed time (and the current step's, once it differs), failed with **Retry now**) and, once ready, the keyed Slot `bot-core.connector.panel` that `main.conversation`'s registration declares (entry key: the connector id; owner props `ConnectorPanelProps` of `src/connector-panel-contract.ts`: the bot, the session, the view and `openStream(name)`); a connector whose browser part is not loaded says so. A request is listed at the top of the Actions panel of every session of the bot (its reason as text only, and **Open {panel}**).
- **Menu bar entries** are bot-core's own list (`client/shell-menu.ts`, `createShellMenu().register({ id, order, label, icon, run, pressed?, disabled? })`, where `pressed` and `disabled` return observables; `run` also gets the shown session's id), not a DSH Slot; `client/wiring/shell.ts` registers the built-in ones.

**Re-checking on DSH upgrades.** `client/` may not import `@deepseek-ai/dsh-client-ui-*` (design rule 30), so the shell copies parts of `@deepseek-ai/dsh-client-ui-conversation` 0.2.2-rc.5: the phase derivation of `ConversationMainPanel.tsx` and `contract/snapshot.ts` (`client/shell-phase.ts`), `ConversationWidthControls.tsx` (`client/ShellWidthControls.tsx`) and the `.root` and width-handle rules of `ConversationRoot.module.css` (`client/styles-shell.ts`). The Factory's own CSS keys some rules (sticky composer, hero centering, hidden composer while settling) on that module's hashed `.root` class, which the shell cannot carry; `styles-shell.ts` restates them on the Factory's data attributes (`data-conversation-scroll`, `data-composer-seat`, `[data-slot]` anchors). `client/upstream.ts` lists these sources and every other DSH file the shell and the lockdown rely on, each with the `reason` and the bot-core files relying on it (the registrations in ui-conversation's `apply.ts`, the Chat view id, ui-subagent's Chat-only pattern, ui-session's `adapter.current`, the renderer's child authorization, anchors and session remounts) with their SHA-256; `test/shell-upstream.test.ts` fails when a file's hash differs. It reads them from the repository's root devDependencies, pinned at `UPSTREAM_DSH_VERSION` (the version every package's `engines.dsh` and DSH dependency names; `test/dsh-version.test.ts`), so it always runs.

## Bot files (`botFiles` Remote)

DSH's file features (file links, the Files sidebar, previews, @-files) read a session's directory with the Host's file system (`workspaceFiles`) at the session's `cwd`, `/home/bot/workspace`, which is no Host path. bot-core registers a read-only Host Remote, `botFiles`, that serves a bot session's files from the bot's environment instead; the bot file viewer (below) uses it; the browser face is `src/client/files.ts`. Its methods and semantics mirror `@deepseek-ai/dsh-api-workspace-files` (types in `src/shared/files.ts`):

| Method                                                                            | Returns                                                                                          |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `stat(sessionId, path)`                                                           | `{ absolutePath, version, bytes? }` of a regular file                                            |
| `read(sessionId, path, { offset?, limit? })`                                      | one page of UTF-8 lines, `{ …stat, offset, text, lines, eof }`                                   |
| `readBytes(sessionId, path, { range?, baseFile? })`                               | a byte window or the complete file, `{ …stat, offset, base64, eof }`                             |
| `list(sessionId, path)`                                                           | direct children of a workspace directory, `{ path, entries, truncated }` (`""` is the workspace) |
| `search(sessionId, { query, excludedPaths?, includeHidden?, respectGitignore? })` | `{ matches, truncated, incomplete }` by name or relative path                                    |

Differences from `workspaceFiles`: the session is a plain `sessionId`; bytes come base64-encoded in `base64` (bot-core's Remotes are JSON); there is no `changes` feed (the SSH file system cannot watch); failures are `bot-file/…` codes with the same suffixes and details (`not-found`, `outside-workspace`, `too-large`, `not-text`, `not-regular-file`, `not-directory`, `search-failed`) plus `not-bot-session`, `unavailable` and `permission-denied`, besides `gateway/bad-request`.

**The wire contract.** `src/shared/remote-contract.ts` declares every method of the `bots`, `botFiles` and `botChannels` Remotes: its wire arguments in order (and which may be omitted), whether it streams and whether it takes a trailing `signal` (ids `@1outres/dsh-bot-core#<namespace>/<method>`). Both faces are generated from it. On the Host, `src/host/remote-contract.ts` registers it with `ctx.typert.register` as strict definitions: DSH's Gateway dispatches an endpoint by its strict definition when one is registered, and only otherwise derives the arguments from the method's source text (`Function.prototype.toString`), where esbuild may rename a parameter that collides with a module-level name (`options` became `options2`, and `readBytes` refused the browser's `options`). `test/remote-contract.test.ts` checks the contract against the Host methods' declared parameters; `test/remote-contract-bundle.test.ts` builds `src/index.ts` with the options `pnpm build` uses, loads it, and checks that every `@Remote` method of the built Services is dispatched by a strict definition whose arguments are the browser's.

**In the browser.** typert registers a Remote package only once, so bot-core mounts its Host Remotes as one contribution: `src/client/remote.ts` declares each namespace's face and composes the descriptors from the contract (a new namespace joins the same contribution), and `client/store.ts` (`mountBotCoreRemote`) mounts it once when the client half applies. A failed mount is final and visible: it is logged with `console.error` and its cause, the Bots section says that bots could not start in this page, and the file viewer reports that the Remote could not be mounted (not `bot-file/unavailable`, which means the Host could not reach the bot's environment). The browser types every file failure (`client/file-failure.ts`): a Host refusal with a known `bot-file/…` or `gateway/bad-request` code, a connection failure (the call threw), a mount failure, or a protocol failure, worded apart from `unavailable`: the Gateway refused the call's shape (`gateway/arguments-invalid`, `input-invalid`, `signature-invalid`: the two faces' contracts disagree), an unknown code, a malformed refusal or result, or a rejection that is not a `BotFileError`. Each protocol failure is logged once with `console.error`, with the raw response.

- **Who may read.** Only a session bot-core recorded as a stored bot's (its Main, `createSession`, an adopted fork; the `sessions` table): anything else, a deleted bot's sessions included, is refused with `bot-file/not-bot-session` before any file system is touched. **Known limit:** a bot's subagent sessions are not recorded as the bot's (they are not navigable sessions), so their files are refused too; the parent session reads the same workspace.
- **Through the VM, never a Host path.** `botFiles` reads a bot's files through its environment only (with `@1outres/dsh-bot-vm` they are on the bot's own workspace volume, which the Host never mounts): the bot creates whatever it likes there, symlinks included, and a link resolves inside the VM, where the Host's files are not.
- **Which file system.** The one inside the bot's own composed preset, never the Host's. bot-core puts its own row `env-bot-core-files` (`@1outres/dsh-bot-core/files`) into every bot's isolated `bot-environment` group, right after the environment's rows. While that preset revision is mounted — registered presets are mounted eagerly, so this holds for a cold session with no Agent — the row hands the group's `fs` and `subprocess` to the `bot` service; it hands over a service only if it lives in a realm a group isolates (a row placed elsewhere hands over nothing). The row carries the revision's token: an HMAC, with a secret bot-core draws on every load, of the composition's digest without that row. bot-core serves only what the row of the **currently registered** revision handed over, so a retired revision still mounted for its Agents (or re-attaching when its row restarts) never wins, and other Host code cannot hand bot-core a file system for a bot (the attach method sits under a symbol, outside the `Bot` contract, and needs that token). Without the registered revision's row (the preset not registered, the environment not ready): `bot-file/unavailable`. Reads use that revision's SSH connection (the one its Agents use; a retired revision's Agents keep their own); nothing new is started. Templates and overlays cannot name the row (`@1outres/dsh-bot-core` and `env-` ids are refused there), and an environment's rows may not use its id or plugin either. Adding the row changes every bot preset's revision once, on upgrade.
- **Where.** `list` and `search` stay inside the environment's workspace (a link out of it is `outside-workspace`). `read`, `readBytes` and `stat` accept any path the bot's own user can read in its VM, like `workspaceFiles` accepts any path the session's file system reads, so a link in a transcript to `/tmp/report.txt` previews. `files.confineReads` stays off by default: the only Host-backed directory in the VM is the shared workspace itself, so a read outside the workspace reaches the VM's own disk only (its system files and the bot's home; root-only files stay unreadable), which the bot reads with its own tools anyway. Turn it on to keep reads inside the workspace too. A final symlink is never read. `list` resolves a directory and then lists it in two requests, so a bot swapping it for a link in between can make it list a directory outside the workspace; that directory is inside the VM, so this reaches nothing of the Host's.
- **Search** runs ripgrep inside the VM through the environment's `subprocess` (`rg --files`, ignore rules unless `respectGitignore: false`, VCS metadata never), as `workspaceFiles` does on the Host: one process listing instead of one SSH round trip per directory. `files.search.ripgrep` names the executable: `rg` (default) is resolved by the environment (the base image installs Debian's `ripgrep`; DSH's packaged `rg` is also at the Host's path there), an absolute path is used as is. Without a `subprocess`, or when rg cannot run, `bot-file/search-failed`; there is no file-system walk fallback. A query and each of at most 256 `excludedPaths` are at most 1024 characters. A caller's abort terminates rg.
- **Load.** At most `files.maxConcurrent` calls per bot run at once; the others wait their turn (an abort while waiting rejects at once).

Caps (`files` config, refused rather than silently cut, except listings and searches, which say `truncated` / `incomplete`):

| Field                                                   | Default                                                                                                                                                                                                                                   |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `files.maxBytes`                                        | `2097152` (one page or byte window; at most 32 MiB)                                                                                                                                                                                       |
| `files.maxFileBytes`                                    | `8388608` (complete `readBytes`; at most 32 MiB, since dsh-fs-ssh sends bytes base64, 4/3 larger, in one dsh-ssh frame of at most 64 MiB; `workspaceFiles` defaults to 32 MiB, but here a file travels base64 over SSH and again in JSON) |
| `files.maxLines`                                        | `5000`                                                                                                                                                                                                                                    |
| `files.maxEntries`                                      | `2000`                                                                                                                                                                                                                                    |
| `files.maxConcurrent`                                   | `4` (per bot)                                                                                                                                                                                                                             |
| `files.confineReads`                                    | `false`                                                                                                                                                                                                                                   |
| `files.search.maxResults` / `maxEntries`                | `512` / `100000`                                                                                                                                                                                                                          |
| `files.search.timeoutMs` / `graceMs` / `stderrMaxBytes` | `30000` / `3000` / `65536` (timers at most `2147483647`)                                                                                                                                                                                  |

**Deploying.** The bot presets now name `@1outres/dsh-bot-core/files` (`lib/files.js`). After updating bot-core, run a full `pnpm build` (not only `pnpm dev`'s watch, which may not have written the new entry yet) before DSH loads the new `lib/index.js`: a preset naming a missing `lib/files.js` fails to mount, so every bot preset would be unregistered until it is built.

## Bot file viewer and right sidebar lockdown

On a bot session DSH's right sidebar (Files, Terminal, the guide, Browser…) cannot open, and everything that would open it there goes to bot-core's **bot file viewer** instead: a panel of the bot session shell between the chat and the menu bar.

- **Opening it.** The menu bar's **Files** button toggles it (`aria-pressed`; closing it returns focus there). File links in the transcript, @-file chips, a deliverable card's body, skill file links and tool line references open the file in it (at the link's line). DSH's shortcuts, with their default keys (each user may rebind them):

  | Command (DSH id)                       | Web (Windows, macOS) | Desktop      | On a bot session                |
  | -------------------------------------- | -------------------- | ------------ | ------------------------------- |
  | Right sidebar (`sidebar.right.toggle`) | Ctrl/⌘+Shift+B       | Ctrl/⌘+Alt+B | toggles the bot file viewer     |
  | Files (`workspace.files`)              | Ctrl/⌘+Alt+P         | Ctrl/⌘+P     | opens the viewer's file browser |
  | New terminal (`terminal.new`)          | Ctrl+\`              | Ctrl+\`      | refused, with a notice          |

  Linux Web has no default key for the first two.
- **Browser.** The workspace tree is listed directory by directory through `botFiles.list` and drawn with DSH's `sidebar.files.tree` Factory (`client/files/FileTreeView.tsx`); `@deepseek-ai/dsh-client-ui-sidebar-files` is therefore a hard client dependency of bot-core (with `@deepseek-ai/dsh-client-ui-conversation`, in `package.json` `dsh.client.inject`): a profile with either disabled does not start bot-core's browser half. If the Factory is still missing, the viewer says the tree cannot be shown (logged once with `console.error`); there is no substitute tree. The search field searches the whole workspace through `botFiles.search` (after a short pause in typing); the query and its results belong to the session like the tree's expansion, so they stay when the panel closes or a file is opened. There is no change feed: **Refresh** lists the open directories again and re-runs the search (or reads the file again).
- **Preview.** Text and code in pages of 1000 lines (a link's line highlighted with DSH's navigated-line token and scrolled to, earlier and later lines on demand); Markdown (files and documents up to 256 KiB; larger ones show as source) rendered by a small built-in reader, linear in its input, that never emits HTML (raw HTML stays text, only http(s) and mailto links become links, opened in a new browser tab), with a **Source** switch; images (PNG, JPEG, GIF, WebP, BMP, ICO, AVIF, SVG through `<img>`, up to 8 MiB) through `readBytes`; binary, too large, missing or unreadable files say so.
- **Focus.** Opening a file from the tree or the search results moves focus to the preview's heading (Escape still closes the panel); **Back** returns it to that file's row, which the tree marks as current (the search field when the file has no drawn row).
- **Layout.** The panel's left edge is a separator (drag it, ←/→, or Home/End for the narrowest and widest; `aria-valuemin`/`aria-valuemax` follow the shell's width) between 280 px and 70% of the shell; the width is kept in `localStorage` (`dsh-bots:files-width`). Every side panel sits beside the chat while the chat keeps 640 px, overlays it from the right (leaving the menu bar) when it would get narrower, and is a full-screen sheet at 640 px and below (`client/shell/panel-layout.ts`, `data-layout` = `beside` / `overlay` / `sheet`); its header shares the shell header's height and centre line. Escape closes it and puts focus back on the menu bar's **Files** button. Each session keeps its own viewer state, tree expansion and search while the page lives; a deleted bot's are released once a bots list no longer names its sessions. A missing or corrupt stored value falls back to the default with one `console.warn` per key.
- **Other sidebar content** opened on a bot session: an in-app Browser link opens in a new browser tab instead (`window.open(url, '_blank', 'noopener,noreferrer')`, as DSH's default-browser choice does; only http(s)); a plan review handed over as text (`/plan`'s review) shows in the viewer; anything else (Terminal, a submitted plan opened by its call, subagent chat, schedule…) shows a dismissible notice in the shell, worded for the common kinds and generic otherwise, and logs its kind with `console.debug`.

**How** (`client/sidebar/` holds everything that depends on DSH's sidebar internals, wired in `client/wiring/rightbar.ts`; each source is pinned in `client/upstream.ts`):

- **Lockdown.** bot-core registers its own `rightbar.session` entry (`client/sidebar/SessionRightbar.tsx`) at `BOT_SESSION_PRIORITY` while the main view shows a bot session or one not classified yet, through the same single-attempt registration as the shell: `rightbar.session` is a single Slot, so DSH's sidebar seat (its guide, controls and every tab body) does not render then, and DSH's seat closes the frame's right column as it leaves. Every way into the sidebar (the shortcuts, file links, the strip's controls) acts through `ctx.sidebarRight` on the shown session's layout store, which nothing draws for a bot session.
- **Routing.** `ctx.sidebarRight.openResource` needs that store to exist (it throws otherwise), so bot-core's entry declares DSH's own store handle. bot-core reads it only from the head of `conversation.session.header.corner`, where DSH registers its expand button with the seat's handle and bot-core never registers (`client/sidebar/store-handle.ts`), and follows that Slot with `ctx.slots.subscribe`: DSH registers a new handle whenever its effect re-runs, so bot-core re-registers its entry with each new one. Failures of `entriesOfSlot` and `subscribe` are not caught. The entry's props say which it got (`handle: "present"` with DSH's store props, or `"missing"`). A tab type `@1outres/dsh-bot-core/file` (kind `bot-core.file`, band `extension`, pattern `dsh-resource://file/session/**`) claims a file address only when its session is classified as a bot's (`canOpen`), so other sessions' files open in DSH's viewers as before. After every change of the bot session's layout, bot-core sweeps it (`sweep-plan.ts` plans, `sweep-run.ts` acts, each action failing on its own with `console.error`): it reads each new tab's address and navigation parameters (`tabDomain.occurrence(…).navigation`), routes it as above, closes every tab (but a lone guide, which DSH keeps) and collapses the column. Only the tabs of the layout the store restored when the entry mounted (saved earlier) are closed without being opened; an open landing in the same tick is routed. A toggle is a change from collapsed to expanded, so a collapse that does not take never makes the viewer flap. The sweep runs in a layout effect of the commit the open caused; opening an external link from there still is not inside the click handler, so a strict popup blocker (Safari's, say) may block it. A swept Terminal tab never starts a shell: DSH starts one only when a terminal body mounts.
- **Status** (`client/sidebar/lockdown-status.ts`): whether the handle is present, how the registration stands, and whether the sweep broke (a tab's navigation could not be read: DSH's tab domain no longer answers as expected). File links reach the viewer only with the handle present, the registration not refused and the sweep not broken; otherwise the viewer's browser says that file links cannot open here.
- **Fail closed.** Without DSH's store handle (a DSH change, before DSH registers it, or without ui-sidebar-right), the entry still renders nothing, so no stock tab ever shows on a bot session; file links then fail inside DSH. A refused registration is final (logged, no other priority tried): the shell says the sidebar could not be locked and the Bots section shows the refusal. Only then can DSH's own seat draw a bot file tab, and its body (`client/sidebar/RefusedFileTab.tsx`) shows only that refusal, never the file.
- Without DSH's right sidebar plugin none of this is registered (nothing can open there anyway).

**Known limits.**

- Not routed to the viewer, because DSH runs them on the Host: the file context menu of ui-open-in-app (it checks the file with the Host's `workspaceFiles.stat`; "copy path" and "open in app" act on a Host path, which for an absolute path names a Host file of that name), the open and reveal actions of presented-file cards, and dragging a file out of the transcript. Deliverables are routed only for a card's body click (its preview).
- Before the sweep closes a routed file tab, DSH's sidebar pins its address in the resource model (`tabDomain.sync` → `ctx.resources.pin`), so DSH's file provider asks the Host's `workspaceFiles` about it once: a workspace-relative path resolves under `/home/bot/workspace` on the Host, which does not exist (and must not, see above); an absolute path (`/tmp/report.txt`) is looked up on the Host, as DSH's own preview would. Only metadata is read and the answer is dropped; bot-core cannot avoid it without changing DSH.
- While a bot session is on screen, bot-core's `rightbar.session` entry also stands in for DSH's in the hidden views of other sessions that the sidebar retains (only tab types with `keepMounted`, such as the experimental Forge changes tab, retain them): those bodies remount when their session is shown again (accepted: it concerns only such tab types).
- A submitted plan opened by its call cannot be shown (a plan review waiting for an answer shows in bot-core's own card, "Interactions").
- Subagent chats, schedules and terminals cannot be opened from a bot session.
- @-file suggestions in the composer still search the Host (and find nothing).

## Channels

A channel plugin connects bots to a messaging service (`@1outres/dsh-bot-discord`). The contract is `src/channel-contract.ts` (re-exported from the package entry): the channel declares what it can carry, bot-core does everything that is not specific to the service, and the channel only presents and converts.

- **Registration.** `registerChannel(channel)` checks the descriptor (`checkChannelDescriptor` in `src/shared/channels.ts`: id `[a-z][a-z0-9-]*`, camelCase field keys, English labels, valid patterns and bounds, `owners` naming a list field) and the capabilities (`host/channels/capabilities.ts`), and refuses a taken id. `channels()` lists them by id.
- **Capabilities** (`BotChannelCapabilities`): `attachments` (`maxCount`, `maxBytes`; absent: text only), `files` (`maxBytes`; absent: the bot cannot send it files), `turns` (turn states), `interactions` (`question`, `approval`, `plan-review`), `commands` (`stop`, `status`) and `connectorActions` (`true`; needs `owners`). An output the capabilities do not carry is never sent to the channel, and nothing replaces it there: the Web UI still shows everything.
- **Settings, schema-driven.** A channel declares its fields: `secret` (a token), `text` (one line, optional pattern, or `choices` to pick from; an optional field lists `""` among them) and `list` (distinct items, `minItems`/`maxItems`, optional item pattern), and may name a `guide` (an https page on setting it up). Labels and descriptions are `{ en, ja? }`, shown in the browser's language (`locale.resolveText`); a field's description is its row's tooltip, never text on the page. The **Channels** section of a bot's settings shows one group per registered channel: a title row with the connection state and the switch that turns it on, one row per field (a secret through Set / Replace / Remove, a text field saved on Enter or leaving it, a choice when picked, a list when leaving it), and **Setup guide ↗**. Every change saves the channel's whole settings at once, over what the change before it stored (`client/serial-saves.ts`); a required field that is missing, and an empty owners field (amber), mark their rows. The values are validated again on the Host (`parseChannelChange`: every text and list field, trimmed; list items deduplicated; unknown keys refused).
- **Owners** (`host/channels/owners.ts`). `owners` names the list field of the channel's ids of the bot's owners there: the people who can instruct the bot as its owner and decide its connector actions (the same list for both). bot-core, not the channel, compares a message's sender with it. Absent, or an empty list: nobody on the channel is the owner, and the settings form says so under the empty field.
- **Storage.** Non-secret values and which secret fields are set: the `channels` table of the storage domain `dsh_bot_channels` (version 1, `host/channels/domain.ts`, key `<botId>:<channelId>`), apart from the bot records. Secret values: one record per bot and channel in DSH's credential store (`ctx.credentials`, key `bot-core/channel-<channel>-<bot>`, a `grant` whose payload is `{ version: 1, secrets }`). The browser never receives a secret: views carry `secrets: { token: true }` only, and a save sends `{ op: "keep" | "set" | "clear" }` per secret (absent is keep). A deleted bot's settings and secrets are removed. Without the `credentials` service the channel features (and the `botChannels` Remote) stay off.
- **Connections** (`host/channels/hub.ts`). For every listed bot (one with a Main session) whose settings for a registered channel are enabled and complete, bot-core calls `connect(link)` with the settings (secrets included, required ones never empty) and keeps the connection until the settings change (then it closes it, waits for the close, and connects again), the bot leaves the list, the channel unregisters, or bot-core unloads. A `connect` that throws is shown as failed; `report` sets what the dialog shows (`connecting`, `connected` with the account, `failed` with the reason). The status also says `off`, `incomplete` (which required fields are missing) or `waiting` (the bot is being created).

Everything a link carries concerns the bot's **Main session** only; other sessions of the bot, subagents included, are never delivered to or reported from.

**Outputs** (`BotChannelConnection.receive`; `host/channels/outlets.ts` gives each connection one output at a time, in the order the Main session produced them, the next once the previous settled; a failure is logged, and for a file reported to the bot):

| Output                                                            | When                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `reply`                                                           | every `assistant/message` the Main session commits with text (its text blocks, trimmed, joined by a blank line; reasoning and tool calls left out; an interrupted one flagged), whoever started the turn, except after the turn called `stay_silent` (below)                                                       |
| `turn`                                                            | the Main session's `turn/start` (`started`) and `turn/end`: `completed`; `cancelled` (`by: "user"` for a stop, else `system`); `failed` with the model's error, a blocked turn, or a reply cut at the output limit. Ends DSH writes after the fact (`interrupted`, `forked`) are not sent                          |
| `file`                                                            | the files the Main session's turn presented with `present`, after the turn's last reply and before its end (below)                                                                                                                                                                                                 |
| `interaction-opened`, `interaction-updated`, `interaction-closed` | a question, approval or plan review of the Main session waits for a person ("Interactions" below), its timed wait changes, and it settles (answered, by the Web UI or which channel, with the answer, or withdrawn); a connection made while one is open gets it first                                             |
| `connector-action`                                                | only to a channel with `capabilities.connectorActions`: a connector action of the bot was created or changed (the whole `ConnectorActionView`: preview, tool, times, state, decision and result); a connection made while some are open (pending, approved, running) gets them first ("Connector approvals" below) |

**Inputs** (`host/channels/conversation.ts`; none rejects, each answers a typed result):

- `deliver({ place, sender, sentAt, text, attachments })` calls DSH's `sessionController.prompt`, the very Remote method DSH's Web composer calls for a plain Enter, from the Host (so the caller is the owner: a `user` message with a fresh `rpcId`). `clientTimeZone` is the Host's time zone. While the Main session is idle the mode is `queue`; while it runs a turn it is the composer's **busy Enter** preference (`ui-conversation.busyEnter`, read through the Settings service; `queue` when it is not set). The content is built as the Web composer builds it (`host/channels/inbound.ts`):
  - the **text starts with a header line** bot-core writes (`host/channels/header.ts`; the channel states only facts): `[<channel> · <place> · <display name> (@<handle>[, owner][, bot])]`, then the message's text on the next line (the header alone for images without text). The place is `DM` for `{ kind: "direct" }`, the only kind so far. `owner` when the sender's id is in the owners field of the bot's settings. Names are folded (NFKC), put on one line (control and format characters, line breaks; as `host/one-line.ts` does for connector event summaries) and stripped of `[`, `]`, `(`, `)` and `·`, and a handle also of `,`, `@` and spaces, so a name can neither end the header early nor claim a role;
  - each **image** as an image part, before the text as DSH's composer orders them (`{ type: "image", mediaType, data, name }`, the composer's inline form), for media types DSH's `attachments.imageLimits` accepts, within its per-image, per-message count and per-message byte limits; DSH then normalizes and stores them, and refuses them when the model takes no images;
  - every **other file** (an image type DSH does not take included) is saved in the bot's environment, in a new folder per message: `<workspace>/.inbox/<UTC yyyymmddThhmmssZ>-<channel>/<name>` (`-2`, `-3`… when taken). Names are made one safe path segment (no directory part, control or format characters, leading dots or dashes; at most 120 UTF-8 bytes, the extension kept) and distinct within the message (`name (2).ext`). The text then lists their absolute paths and sizes. DSH's `FileSystem` writes UTF-8 text only, so bot-core writes them with `sh` through the environment's own `subprocess` (the VM, as the bot's user: a temporary file, then a rename that refuses to replace anything), never through the Host's file system. DSH's own path for non-image files (stored on the Host, named to the model by a Host path) would be unreadable in the VM;
  - limits: the channel's `attachments` and bot-core's `channels.attachments` config (`maxCount` 10, `maxFileBytes` 25 MiB, `maxMessageBytes` 50 MiB), checked on the declared sizes before anything is read; a read longer than its limit is refused too. Nothing is passed unless every attachment made it.
  - Failures (`BotDeliveryFailure`, an English message for the person): `closed`, `empty`, `no-main-session`, `too-many-attachments`, `too-large`, `unreadable`, `environment-unavailable`, `save-failed`, `rejected` (DSH refused the prompt). The receipt names the session, the mode, the number of images and the saved paths.
- `run("stop" | "status")` (`host/channels/commands.ts`; only commands the channel declared; `link.commands` gives their descriptions, `{ en, ja }`): `stop` calls `sessionController.cancel`, the method the Web UI's stop button calls (the turn ends, queued messages stay), and answers `idle` when nothing runs; `status` reports the activity, whether the Main session's Agent is loaded, its model (`agent.model.current()`) and the people's messages waiting in its inbox.
- `answer(interactionId, answer)` and `hold(interactionId)` (`host/interactions/board.ts`, scoped to the bot's Main session): the first accepted answer from anywhere settles the interaction; later ones get `not-open`, an answer that does not fit `invalid`, one DSH could not take `failed` (the interaction stays open).
- `decide(actionId, decision, person)` (`host/connectors/approvals.ts`): a person's decision on a pending connector action, `person` being the channel's own id of whoever pressed (the channel authenticates it). Taken only when the channel declares `connectorActions` and `person` is in its owners field in the bot's settings of the channel; otherwise `not-approver` (a channel without the capability, or an empty list, lets nobody decide). Also `not-found`, `settled` (with the current view) and `closed`.
- `pendingActions(person)` (`host/connectors/approvals.ts`): the bot's pending connector actions, oldest first, for the same owners only (a preview can hold personal data): anyone else gets `not-approver`, and `closed` once the link's signal aborted. A channel builds its own list of them from it (Discord's `/pending`).
- `connectorAction(actionId)`: the bot's action as the ledger keeps it now (`undefined` once it is no longer kept, for another bot's id and for a channel without `connectorActions`). A new connection only gets the open actions, so a channel that keeps what it showed (Discord keeps its cards) reads with it what became of the others while it was not connected.
- After the link's `signal` aborts, inputs answer `closed` and reports are dropped.

**Sending files.** A bot sends files with DSH's own `present` (`@deepseek-ai/dsh-tool-present`): bot-core puts it in every bot's preset group as its own row `env-bot-core-present` (after the web bridge row), so it runs on the group's `fs`, the bot's environment, and resolves relative paths from the session's directory there. Templates and overlays cannot name the package (nested rows and environment rows included), and a template's `hostTools` cannot grant the Host's `present`, which reads Host paths. A presentation shows in the Web UI as DSH's file card, which the bot's file viewer opens, in every session. Only the bot's **Main session** sends it on: the feed (`host/channels/feed.ts`) collects the files of each `deliverables/presented` event of the Main session's running turn (`host/channels/presented.ts`; a path presented again in the same turn is kept once, in the place of its first presentation, with the description of its latest one), except those presented after the turn called `stay_silent`. Web sessions, schedule runs and subagents only show their cards in the Web UI and tell nothing. When the turn ends (any end DSH writes live: `completed`, `cancelled`, `failed`), `host/channels/presented-delivery.ts` reads each file through the environment's `fs` (`host/workspace-file.ts`: a final symlink is not followed, anything resolving outside the workspace is refused) and queues it as a `file` output, with its description as the caption, on every connection that takes files; `host/channels/sequence.ts` holds the turn's `turn` output, and anything the Main session produces after it, until every file is queued (reading is bounded by 60 s), so each connection gets the turn's last reply, then its files, then its end. Limits: each channel's `files.maxBytes` and `channels.files.maxBytes` (25 MiB, at most 32 MiB: the file travels base64 over SSH). `present` answers before any of this, so what did not reach a channel (outside the workspace, unreadable, larger than a limit, a channel's error, the environment not ready) is told to the Main session afterwards as one notice per turn (`host/channels/presented-notice.ts`; topic `file`, source `{ kind: "bot-file", form: "notice", summary }`, timing `next-turn`; "Connectors", Notices), listing each such file with what happened per channel; it asks the bot to make a file that was outside the workspace, unreadable or too large fit and present the new one, and not to present a file again unchanged (after a channel's error or an environment that was not ready it tells the user instead), so a failing channel does not loop. Nothing is read or told while no connection that takes files is attached: the Web UI's card is enough then. The collection lives in memory only: files a turn presented before DSH restarted are not sent when it resumes (the cut turn's end is one DSH writes after the fact), nothing replaces them, and no notice tells of them; their cards stay in the Web UI.

**Staying silent.** The same row registers `stay_silent` (optional `reason`, shown only in the session): it lets the Main session decide that a turn has nothing for the user. A call goes to the `bot` service under a symbol with the token (`host/channels/stay-silent.ts`), refused outside the bot's Main session (another session or a subagent gets a tool error naming why) and unless the token is the registered revision's, and marks the session's running turn silent (`host/channels/silence.ts`: bot-core follows every session's `turn/start` and `turn/end`; a turn starts not silent and its end forgets it; a call while no turn is known to run fails). The feed (`host/channels/feed.ts`) then withholds that turn's remaining `reply` outputs and the files it presents from then on; they stay in the Web UI and the session history, and its `turn` outputs still go out. Replies committed before the call have already been sent and are not taken back, so the tool's description tells the model to call it before writing any reply text. Its result names the silenced turn.

## Connectors

A connector plugin gives bots tools for an outside surface (a desktop or browser in the bot's environment, Gmail, a calendar…). The spec is `docs/specs/bot-connectors.md` (repository root); the contract is `src/connector-contract.ts` (re-exported from the package entry). A connector is a definition: its tools and each tool's default permission, which sessions see them, its per-bot settings, what it needs of the bot's environment and how to prepare it, and an optional resident resource per bot. bot-core owns the rest: enablement, readiness, permissions, the ledger of actions that ask first, notices, serialization and result images. People manage them in the **Connectors** section of a bot's settings (below); the `bot` service and the `botConnectors` Remote carry the same operations.

- **Registration.** `registerConnector(connector)` checks the descriptor (`host/connectors/catalog.ts`: ids `[a-z][a-z0-9_]*`, `connector` reserved; `sessions` `main` | `bot`; settings fields `toggle` / `choice` / `integer` / `text` with English labels and valid defaults; `minimumSpec` (keys of the bot's spec, positive integers); `preparation.prepare` and `attachment.open` functions; per tool a description, a default `permission` (`allow` | `ask` | `disallow`, always stated), `preview` and `execute`, optional `recheck`, `snapshot`, `exclusive` key and `maxResultChars` (default 32 000, at most 256 000); `ask.waitMs` 0–10 min (default 60 s) and `ask.ttlMs` above it, at most 30 days (default 24 h); arguments as dsh-tools' `parameters` or a JSON Schema `inputSchema`, compiled by dsh-tools' own compiler) and refuses a taken id or a tool name another connector already makes. A tool's name among the bot's tools is `<connector>_<tool>` (at most 64 characters). `connectorTools<A>()` gives `tool` (arguments typed from the schema) and `schemaTool` for a connector whose resident resource is `A`; `defineConnectorTool` for one without.
- **Enablement and settings.** A connector starts off for every bot that exists when it registers. A new bot starts with the connectors of the creation options its creator turned on in the New bot dialog (spec 14). bot-core owns the options (`BOT_CREATION_OPTIONS`, now only `workstation`, shown as **Turn on the desktop and browser**, on by default) and a connector declares the one it belongs to with `creationOption`; the dialog shows an option only while `bots.creationOptions()` offers it (some registered connector belongs to it, with what its connectors need), and no other connector; with the environment's capacity it offers too, the dialog shows the VM the bot gets (read-only: the VM page changes it later), starts an option off and disables it when the Host cannot give what it needs, and disables Create when no VM can be made. `bots.create({ name, avatar, workstation, timezone, language })` takes every option as a boolean: bot-core selects every registered connector of an option on (an option on that none belongs to refuses the creation before anything is stored; off enables nothing), stores them enabled with their default settings (events off) right after the bot's record and before announcing the bot, after the bot's initial spec (made from the environment's capacity and the options' connectors' `minimumSpec`; see "The bot's VM spec"), so the VM is made once with it and they prepare as soon as the first ensure resolved. `configureConnector(botId, connectorId, { enabled, values })` (or `botConnectors.configure`) stores them, validated against the fields as untrusted input, in the `settings` table of `dsh_bot_connectors` (version 2, compatible with 1; key `<botId>:<connector>`). **Requirements stay closed** (`connectorSwitchBlock` in `src/shared/connectors.ts`, checked by the settings store inside its serial save): a connector is turned on only after every connector it `requires` (refused with `turn on Desktop first: Browser needs it`, or `… needs connectors that are not installed (…)`), and turned off only after every connector requiring it (`turn off Browser first: it needs Desktop`); nothing is switched in a chain. **The spec stays closed** too: a connector whose `minimumSpec` the bot's spec does not give is not turned on (`Desktop needs 4 GiB of memory or more: raise it on the bot's VM page first`), and the bot's spec is not lowered below what an enabled connector needs; both checks run in one save queue shared by the connector settings and the specs (`host/save-queue.ts`), each reading the other's state. Keeping a connector's state is never refused, so settings stored before this rule (a connector on while one it requires is off) are left as they are and either may still be turned on, or the dependent off. A creation enables its connectors in requirement order. Tools of a disabled connector are not registered. A deleted bot's settings go.
- **Readiness** (`host/connectors/readiness.ts`, `ConnectorReadiness`): `disabled`, `unavailable` (something it needs is missing, by `cause`: `accounts`, `environment` not ready, or `requirements` — a required connector off, missing, waiting or failed; the Web UI words it by cause), `preparing` (since when, and its stage with the time that began: `requirements` while connectors it requires prepare; `queued` behind another preparation of the bot; `running` with the step `prepare` reports), `ready`, `failed` (reason, retried at `retryAt` with a doubling backoff from 5 s to 5 min; `retryConnector` now). A connector without preparation is ready once enabled. Otherwise its `prepare` runs once per environment generation (every resolved ensure: it may be a new VM) and settings values, one at a time per bot across connectors; a change of what is wanted aborts it. Disabling a connector this process prepared runs its `unprepare`. Tools stay registered whatever the readiness (a call while not ready fails with why); an approved action waits until its connector is registered and ready. `connectorStates(botId)`, `onConnectorStateChange` and `botConnectors.watch(botId)` report it all.
- **The bot's VM spec** (docs/specs/bot-vm-spec.md). Each bot has its own CPUs, memory and disk (`dsh_bot_environment_specs`, written only by `host/environment-spec/store.ts`): a new bot gets `initialEnvironmentSpec` (`shared/environment.ts`) of the environment's `capacity()` read when it is created: each key of `DEFAULT_BOT_ENVIRONMENT_SPEC` (4 vCPU / 6 GiB / 20 GiB) brought within the capacity, never below what the connectors of its creation options need; when the capacity cannot be read or cannot give that, the creation is refused before anything is stored (`Desktop needs 4 GiB of memory, but this Host can give a bot's VM at most 3 GiB`). A bot stored before specs gets, before its first ensure, what its environment runs with (`BotEnvironment.inspect`), so it keeps its machine and is not restarted, or the initial spec when it has no environment yet. The target of every ensure carries the spec; a saved change ensures the bot again at once (a running VM is stopped, changed and started). Connectors never change it. The VM section (`client/environment/`, order 250) edits it through the `botEnvironment` Remote: changed values are checked against the environment's `capacity()`, a disk only grows, and nothing goes below what an enabled connector needs; saving asks to restart the VM first.
- **Where tools run.** bot-core calls every hook from its Host process only. `BotConnectorRun` carries the bot, its settings of the connector, its environment, the trigger (`call`, or `approval` with the action id and snapshot), an abort signal, the resident resource and, for a call, the caller (session and images). The environment (`host/connectors/environment.ts`) is the registered revision's own `subprocess` (the bot's VM, as its user): `exec` (binary stdout, a timeout, a cap), `spawn` (streamed stdin and stdout), `readFile` / `writeFile` (with `sh` there); every call rejects while the environment is not available. Credentials of outside services stay on the Host.
- **Panels and status** (spec 13). A connector may declare `panel: { title, icon, streams }` (`icon`: one of `CONNECTOR_PANEL_ICONS`, `desktop` / `browser` / `mail` / `calendar` / `files`, the glyph bot-core draws for its menu bar button) and `status: { read, subscribe }`. Each stream (`{ name, parse, open(run) }`) is opened by the `botConnectorStreams` Remote (`open(botId, connectorId, stream)`, a stream with an uplink; `host/connectors/streams.ts`): only for the DSH Host's `owner` Peer (as `decide`), only while the connector is ready for the bot, at most 8 per bot and connector; every browser item goes through `parse`, and `run.signal` aborts when the viewer leaves or the connector leaves `ready` for the bot (released with the attachments). A connector's `status` (`{ note?, request? }`, read only while it is enabled for the bot, `host/connectors/statuses.ts`) is part of `BotConnectorView` and of `onConnectorStateChange`.
- **Resident resources** (`host/connectors/attachments.ts`): `attachment.open` runs at the first run that needs it; the resource is shared by later runs and disposed when the connector leaves `ready` for the bot, unregisters, the bot is deleted or bot-core unloads; one whose `ended` settled is opened anew by the next run. A call is never repeated.
- **Images** (`host/connectors/images.ts`): `run.caller.images.admit(image)` stores it in DSH's attachments only when the calling Agent's model declares image input, and answers the size that model is sent (`readImageRequest`) and the source size; a result's `images` reach the model as image blocks (the connectors row renders them). The ledger never keeps images.
- **Permissions** (`host/connectors/permissions.ts`): the tool's default unless the bot overrides it (`permissions` table, key `<botId>:<connector>:<tool>`). `connectorPermissions` / `setConnectorPermission` (or `botConnectors.setPermission`). An `allow` call runs at once: no action, no snapshot, no preview.
- **What the bot sees** (`host/connectors/tools.ts`). bot-core's row `env-bot-core-connectors` (`@1outres/dsh-bot-core/connectors`, sealed with the revision token) registers the tools of the bot's enabled connectors whose permission is not `disallow`, and `connector_pending_list` / `connector_pending_cancel` while the bot has a visible connector tool or an open action, each with a step-time condition (dsh-tools `register(definition, { when })`): tools of a `main` connector and the pending tools show in the bot's Main session only, those of a `bot` connector in every session of the bot (subagents included). A call that reaches bot-core anyway is refused unless the token is the registered revision's and the caller may use the tool. An `ask` tool's description says it asks first.
- **Calls.** `allow` runs the call (`host/connectors/execution.ts`, the only caller of `execute`, `recheck` and `snapshot`, design rule 39); calls of one `exclusive` key run one at a time per bot and connector (`host/connectors/exclusive.ts`). A result is `{ text?, data?, images? }`: text and data (as JSON) cut at `maxResultChars`.
- **`ask`** (`host/connectors/broker.ts`). The call does not run: a tool's `snapshot` reads, with I/O, what the preview cannot show from the arguments (a message a reply quotes); bot-core generates the preview from the arguments and snapshot and stores a **pending action** with the arguments, snapshot, preview, calling session and expiry in the `actions` table (written only by `host/connectors/ledger.ts`, design rule 40). An equal call while one is pending gets that action. The call then waits up to the tool's `waitMs`; otherwise it returns "awaiting approval" with the action id and expiry. A stopped turn only ends the wait.
- **The state machine** (`host/connectors/action.ts`, pure): `pending → approved → executing → succeeded | failed | interrupted`, `approved → failed` (its connector was not registered and ready before expiry), `pending → rejected | expired | cancelled`. An approved action runs once, after `approved → executing` is stored, with the stored arguments and the snapshot in its trigger; `recheck` may refuse it. A succeeded action keeps its result's data and text. Ended actions stay 7 days.
- **Decisions** ("Connector approvals" below). Only the bot's owner decides, in the Web UI or through a channel's approvers; the `bot` service has no decision method. `connectorActions(botId)` and `onConnectorActionChange` are read-only.
- **Start-up.** An action left `executing` becomes `interrupted` (never run again) and the bot is told; an `approved` one runs once its connector is registered and ready; pending ones get their expiry timers back.
- **Connectors section** (`client/settings/ConnectorsSection.tsx`, order 300, after Channels). It follows `botConnectors.watch(botId)` through one stream per bot shared with its nav badge (`client/connectors-hub.ts`, the worst readiness among enabled connectors: failed red, unavailable amber, preparing gray, ready green), so a readiness change shows at once. The watch also re-yields when a connector registers or unregisters (`ConnectorPanel.subscribe`). One card per registered connector, in registration order (a note when none is): its name, description, readiness (the stage, the elapsed time and the connector's hint while preparing, the reason while waiting or failed, the automatic retry time and **Retry now** for a failed one) and what turning it on implies (which sessions see the tools, whether it prepares the VM).
  - **The list** (`client/settings/ConnectorsSection.tsx`): group **Accounts** first while a connector acts as a provider's accounts (one row per provider: its state, the bot's account count, the way to its page), then **On** and **Off**: one row per connector (no tags), its readiness while on, its switch and the way to its page (`openSettings(botId, "bot-core.connectors", connectorDetail(id))`, `accountsDetail(provider)`; `client/settings/connectors-pages.ts`).
  - **Enablement and settings** are saved as they change: the switch at once (a switch the Host would refuse — a connector it requires off, one requiring it on, or a spec with too little for its `minimumSpec` ("Needs 4 GiB of memory or more. Raise it on the VM page.") — is disabled, with why in the row's meta and on the connector's page: "Turn on Desktop first: Browser needs it", "Turn off Browser first: it needs Desktop"), a choice or toggle when picked, a text or integer field on Enter or leaving it once it passes the Host's own checks (`checkConnectorSetting` in `src/shared/connectors.ts`). The connector's page (`ConnectorDetail.tsx`) shows its readiness (preparing, waiting, failed with **Retry now**), group **Settings** (its fields and its **Events** delivery) and its tools.
  - **Tool permissions** apply at once (one `setPermission` per change; the Host stores them per tool): group **Tools (n)** has one row per tool, its name in the connector (its description is the row's tooltip), Allow / Ask / Disallow (the default's segment titled Default), and while the bot overrides it a Changed tag and a reset button. Picking the default drops the override. **Reset to defaults (k)** drops every override of the connector. Only letting a tool run without asking against its default (`ask` or `disallow` → `allow`) asks first; tightening, resetting and `disallow` → `ask` do not. From 10 tools the group's sticky title gets a filter (names first, then descriptions). A connector with accounts adds one group per account below (As the tool, or its own permission).
  - Confirmations go through the settings flow (`SettingsFlow.confirm`, `SettingsSectionProps.confirm`): the screen shows them, and closing or leaving the section answers no.
- **Notices** (`host/notices/`). An action that ends after its call returned (not one the bot cancelled) is told to the bot's Main session through the outbox, the `notices` table of `dsh_bot_notices` (written only by `host/notices/outbox.ts`, design rule 41), with a fixed message id. Delivery (`host/notices/delivery.ts`) resumes the Main session if needed and hands the message outside any initiator: to an idle Agent with `followup`; to a running one as its topic's timing says (`NOTICE_DELIVERY`): `next-step` topics (`connector`) with `inject`, `next-turn` topics (`schedule`, `event`, `file`) with `followup`. A notice counts as delivered once a `user/message` with its id is recorded; until then each pass checks again and sends it again with the same id after a backoff (5 s, doubling, at most 10 min). The message's source is `{ kind: "bot-connector", form: "notice", summary }` and its text starts with `[BOT CONNECTOR NOTICE]`. Never through `sessionController.prompt`, which would be the user speaking.

## Connections

A connection is an outside account (a Google account) that connectors act as (docs/specs/bot-connectors.md 10). A provider plugin registers the service with `registerConnectionProvider({ id, name, oauth: { authorizationEndpoint, tokenEndpoint, revocationEndpoint?, identityScopes, authorizationParameters? }, identify(accessToken) })`; a connector names it in `connections: { provider, scopes }`. bot-core runs the sign-in and keeps the tokens; the provider only names its endpoints and identifies an account.

- **Storage.** `dsh_bot_connections` (version 1, `host/connections/domain.ts`, written only by `host/connections/store.ts`, design rule 48): `connections` (`conn-<hex>`: provider, label, account `{ subject, email?, displayName? }`, granted scopes, `services` (the provider's connectors whose scopes all were granted), status `active` | `needs-reauth` | `revoked` | `error` with its reason, the token endpoint that issued it, times), `grants` (bot × connection: one account may serve several bots), `clients` (each provider's OAuth client id). Secrets live in DSH's credential store only (`host/connections/vault.ts`): `bot-core/connection-<id>` (a `grant`, `{ version: 1, refreshToken, scopes, subject, email }`) and `bot-core/oauth-client-<provider>` (`{ version: 1, clientSecret }`). Access tokens stay in memory. Nothing of it reaches a bot's environment or the browser.
- **Sign-in** (`host/connections/signin.ts`, `oauth.ts`). The owner starts it in the Web UI (`botConnections.authorize({ provider, services, label?, botId?, connectionId?, origin })`): bot-core keeps an attempt in memory (10 min) with a random `state` and PKCE verifier, and answers the provider's authorization URL (S256 challenge, the identity scopes and the chosen connectors' scopes, the provider's parameters; `login_hint` when signing a connection in again). The browser comes back to bot-core's route `GET /bot-core/oauth/callback` on DSH's web server (`ctx.webServer.register`, a resource route; it checks no cookie, so the one-time `state` is what admits it): bot-core exchanges the code with the verifier and the client secret, requires a refresh token, identifies the account, refuses another account than the connection being signed in again, upserts the connection by provider and subject, stores the refresh token, assigns the bot, and answers a static page (`no-store`, `no-referrer`, CSP `default-src 'none'`). The redirect URI is `<the Web UI's origin>/bot-core/oauth/callback`, so a DSH inside a VPN works: only the browser reaches it.
- **Tokens** (`host/connections/tokens.ts`). `run.connection.accessToken({ refresh? })` answers a cached token or refreshes it, one refresh per connection at a time; a new refresh token from the endpoint is stored. `invalid_grant` marks the connection `needs-reauth`; a connection whose token endpoint is not the provider's current one (a development endpoint, say) is never refreshed there (`error`).
- **Accounts of a bot** (`host/connections/accounts.ts`). Every tool of a connector with connections takes `account` (its email or label; bot-core adds it to the schema and keeps it from the tool's hooks), resolved among the bot's assigned connections that are active and granted the connector's scopes. An Ask preview starts with `Account: <label> <email>`, and the action keeps the connection id: the approved run acts as that account, if it is still assigned and usable. bot-core adds `<connector>_accounts` (Allow). A connector with connections is `unavailable` for a bot without a usable account.
- **Permissions per account.** A bot may override a tool for one account (`setPermission({ connectorId, tool, permission, connectionId })`; key `<bot>:<connector>:<tool>:<connection>`); an account without its own override follows the tool's. `ConnectorToolPermission.accounts` lists them. A tool is shown while some usable account may call it.
- **Remote `botConnections`** (owner only: `this.ctx.invocation.peer.principal.kind === "owner"`, like decisions): `watch()` (providers with their client's state and services, connections with their bots, recent attempts), `configureClient(provider, { clientId, clientSecret: keep | set | clear })`, `authorize`, `rename`, `assign(botId, connectionId, assigned)`, `disconnect` (revokes the refresh token at the provider, then forgets the secret, the connection, its assignments, events and cursors; answers whether the provider confirmed).
- **Web UI.** The bot's Connectors section lists one row per provider its connectors use, opening the provider's page: the OAuth client's state with **Open the dsh-bots settings** while it is not set up, then group **Accounts** (this bot's first): each account's letter, name, email and the number of bots using it, its state, the switch that assigns it to the bot and a `…` menu (**Rename**, in place; **Sign in again**; **Disconnect…**, confirmed), and **+ Add account** (a switch per connector to grant, an optional name, **Sign in with …**; the sign-in opens in a new tab and the group follows the attempt). Each connector's row names the bot's accounts it can use, and its page has its events' delivery. The dsh-bots settings have an **Accounts** section: per provider a group (with a DEV tag for a development provider) of the redirect URI to register (made from this page's origin, with Copy), the client ID (saved on Enter or leaving it), the write-only secret (`SecretRow`) and the provider's **Setup guide ↗** (`BotConnectionProvider.guide`), then the same account rows as a bot's, without the switch (`client/accounts/`).

## Logins (password managers)

Password manager providers (`registerVaultProvider`) connect the owner's accounts in the dsh-bots settings (**Password managers**); their setup secrets stay in DSH's credential store. In a bot's settings (**Logins**) the owner gives the bot items of those accounts, the fields it may fill (username, password, one-time code, passkey), the sites and whether desktop applications may get them. The bot lists them with `credentials_list` and fills them with connector tools that declare `vault: true` (`run.vault`): every value is checked against the login, recorded and fingerprinted, and handed over as `SecretBytes`, never as a string. A leak guard row in every bot's group withholds those values from every tool result, refuses tool calls whose arguments hold one, and records an incident the owner sees in the bot's shell, the Bots list, the settings and the channels that declare `credentialIncidents` (docs/specs/bot-vaults.md). Not guarded: images, and what the bot deliberately sends out of its VM.

## Connector events

A connector with connections may report events (`events: { kinds, delivery, intervalMs, poll(source, cursor) }`).

- **Polling** (`host/events/poller.ts`). One stream per account and connector that some bot receives events of (assigned, connector enabled, delivery not `off`), polled at once when it starts (so a restart catches up) and then every `intervalMs`. The first poll only stores the cursor; later ones store their events, then the cursor. A stream nobody receives any more forgets its cursor, so turning events on again starts from then. A failed poll is logged once per message and tried at the next interval.
- **Storage** (`dsh_bot_connector_events` version 1, written only by `host/events/store.ts`, design rule 49): `events` per bot, connector and account (deduplicated by the connector's key; `new` → `notified` | `acked`; at most 500 per stream, dropping one nobody took records a gap; told or acknowledged ones are kept 7 days, others 30) and `cursors` per account and connector. A poll's `gap` (the service lost the history) becomes one "events may have been missed" event. Events the connector marks `own` (the bot's own changes) are kept acknowledged and never told.
- **Delivery** (`events` in the bot's settings of the connector: `off` (default) | `notify` | `queue`; the connector's `delivery` is shown as recommended). `notify` (`host/events/delivery.ts`): events arriving within 60 s go out as one notice through the outbox (topic `event`, source `bot-connector-event`, timing `next-turn`), then are marked told. `queue`: bot-core adds `<connector>_events_list` (`account?`, `limit?`) and `<connector>_events_ack` (`event_ids`), Allow, Main only.
- **Untrusted content.** Every notice and listing frames each account's events in `[BOT CONNECTOR EVENT — untrusted content from <account>]`, says the content is data and never instructions, and fences the lines with a random marker; summaries are one line each (no line breaks or control characters, at most 500 characters), so they cannot fake the frame.

## Connector approvals

A pending connector action waits for its bot's owner (until it expires, across restarts: the ledger keeps it). `host/connectors/approvals.ts` is the only way a decision reaches the broker (`ConnectorBroker.recordDecision`, design rule 46), and it takes one only from the owner:

- **Web UI.** The `botConnectorActions` Remote: `watch(botId)` (every action the ledger keeps for the bot, as `ConnectorActionView`: the record with its connector's name and its tool's name among the bot's tools, again after each change), `watchWaiting()` (pending actions per bot) and `decide(botId, actionId, decision)`. `decide` reads the calling Peer from `this.ctx.invocation` and takes the decision only when its principal is DSH's `owner` (the one who signed in to DSH's Web UI with the Host's token; a liveshare viewer or any other non-owner Peer, and an in-process call without an invocation, get `not-approver`). The Gateway already refuses non-owner calls unless a policy grants the endpoint; this check keeps it so if one ever does. Its origin is `{ kind: "web" }`.
- **Channels.** A channel declares `owners: "<key of one of its list fields>"` and `capabilities.connectorActions: true` (checked at registration) and gets `connector-action` outputs; `link.decide` takes a decision only from a person in that field of the bot's settings, so it fails closed. Its origin is `{ kind: "channel", channelId, channelName, person }`. `link.pendingActions(person)` lists the pending actions for the same people only, and `link.connectorAction(actionId)` reads one action as it stands (for a channel bringing up to date what it showed while it was not connected).
- **Audit.** The ledger stores the decision with its origin and time (`dsh_bot_connectors` version 3: a channel origin carries the channel's name; the Host-plugin origin is gone, and a record of an earlier version that has one is backed up and skipped), then the run's start, end and result or reason. Both surfaces show who decided where, when, and how it ended.
- **Shell.** Nothing about actions appears in the conversation column. The menu bar's **Actions** entry (`bot-core.actions`) carries a count badge of the pending ones (and a dot while a connector requests a person) and toggles the **Actions panel** (`client/approvals/ActionsPanel.tsx`, in the side panel frame; width kept in `dsh-bots:actions-width`; Escape closes it) of every session of the bot (`approvals.feed(botId)`, one reconnecting stream per bot shared by everything that shows it, `client/approvals/hub.ts`): the connectors' requests first, then the open actions, oldest first, as cards (`ActionCard.tsx`: a state pill and the expiry as a relative time, the preview's title, fields and body, one line `connector · tool · when`, and **Reject** / **Approve** while pending), then group **History** with every ended one the ledger keeps (7 days) as a row (title, connector and when, state pill) that discloses its details in place (how it failed, who decided when it came from a channel, the result, the preview and the arguments). Untrusted text (the preview, the result) is rendered as React text in `<pre>` / `<dd>`, never as HTML or Markdown; a long body or result folds behind **Show all**.
- **Bot rows.** A bot with pending actions shows their count on its row in the Bots section (`watchWaiting`), with an accessible description.

## Schedules

A bot schedules its own work: later (`at`, `after`) or repeatedly (`every`, `cron`), with an optional check command that decides whether a run goes ahead. Everything the user gets is still written by the bot's Main session: a run's outcome reaches the Main session as a notice and the Main replies (or calls `stay_silent`). The spec is `docs/specs/bot-schedule.md` (repository root).

- **Tools** (`plugins/schedule.ts`, row `env-bot-core-schedule` (`@1outres/dsh-bot-core/schedule`) after the connectors row, sealed with the revision token like the other bot-core rows; templates, overlays and environment rows cannot name it). `schedule` (`action`: `create` with `name`, `mode`, `schedule`, `instruction`, optional `check` and `timezone`; `list`; `update` with `id` and the fields to change, `enabled` included, `check: null` removing the check; `delete`; `run`, which starts a run now and answers at once) and `schedule_result` (`{ outcome: "report", report }` or `{ outcome: "nothing" }`, once). `create` and `update` answer with the job and its next 3 runs in the job's local time. Both tools are registered with a step-time condition (dsh-tools `register(definition, { when })`): the Main session sees `schedule`; a `separate` run's own session sees `schedule` (update or delete of its own job, no id) and `schedule_result`; every other session (one opened from the browser, a subagent) sees neither, and a call that reaches bot-core anyway is refused (`host/schedule/tools.ts`, after the same token check as the other rows). No tool selects a model. The descriptions carry the rule for choosing a mode (`MODE_RULE`).
- **Modes.** `main`: the Main session gets a notice with the instruction (and the check's output) and carries it out as part of its conversation. `separate`: bot-core opens a new session of the bot through `Bot.createSession` (titled `Schedule: <name>`), gives it the instruction (and the check's output) as one prompt (source `bot-schedule`), and waits for that turn's `turn/end`; `schedule_result` with a report sends the report to the Main session, `nothing` is only recorded, a turn that ends without it, a failed or cancelled turn, a session that cannot start, or a run longer than 60 minutes fails the run. The session is then archived (it stays reachable from the Web UI: **Show archived sessions** in the bot's menu lists it, and Unarchive opens it again).
- **Timing** (`host/schedule/timing.ts`, pure). Every calendar computation is DSH's: `@deepseek-ai/dsh-schedule` (`parseCronInput`, `resolveEveryOccurrence`) and `@deepseek-ai/dsh-util-time` (`canonicalizeTimeZone`, `parseOffsetInstant` / `parseLocalCalendar` / `resolveLocalInstant`, `Cron`'s fields, `next` and `resolve`, `Duration`), both peer dependencies resolved from the DSH installation like the other `@deepseek-ai/*` ones. DSH's `ScheduleService` is not used: it creates sessions outside `Bot.createSession`. `at` without an offset is local time in the job's zone; `after` becomes an `at` when created; `every` is at least 5 minutes; a `cron` whose minute and hour fields allow two runs less than 5 minutes apart (two minutes of one hour, or the end of a matched hour and the start of the next, 23 → 0 included) is refused. A job's zone is fixed when it is created: the `timezone` argument, else the bot's time zone setting.
- **Language setting.** Every bot created now has `language` (a BCP 47 tag; `BotView.language`, changed with the `bots` Remote's `update` and in the General section, which offers DSH's languages): the browser sends the language it shows bot-core in (its `format.locale`) with `create`. `greeting` fills `{language}` with its English name (`ja` → Japanese). A bot stored before it has none, shown as "Not set", and its greeting says "the language your owner writes in"; nothing guesses one. Replies follow the language the person writes in (the prompt says so); the setting is only for the greeting.
- **Initial workspace files** (`host/workspace-files.ts`). A bot gets `AGENTS.md` and `SOUL.md` in its workspace (docs/specs/bot-system-prompt.md §6), written through its environment's file system (never the Host's), each only when no file of that name is there; once both are, the record keeps `workspaceFiles: 1` and they are never placed again. A new bot's are placed right before its Main's greeting; a bot stored before them gets them once its preset revision is registered and that revision's file system attached (whichever comes last). The `default` template's `agent-instructions` reads both (`instructionFileCandidates: ["AGENTS.md", "SOUL.md"]`). AGENTS.md's "Remembering" section follows the notes (below); a bot's AGENTS.md already there is its own and is never rewritten. The pinned notes `Owner` and `Now` are placed at the same moments, after the files, and recorded apart (`initialNotes: 1`), so a bot stored before notes gets them once without getting back a file it deleted.
- **Time zone setting.** Every bot has `timezone` (IANA; `BotView.timezone`, changed with the `bots` Remote's `update` and in the General section of the bot's settings). A new bot gets the zone of `BotCreateInput.timezone` (required; the New bot dialog's Time zone row, the browser's zone unless changed), canonicalized by the Host (`canonicalTimezone`, DSH's `canonicalizeTimeZone`), which refuses one that is not UTC or an IANA Area/Location. Bots stored before bot time zones ran in the Host's zone: start-up stores that one as theirs once (`migrateTimezones`). The zone is also the `clientTimeZone` of the turns its channels start. Changing it changes the default of new jobs only.
- **Runs** (`host/schedule/runner.ts`, the state machine in `host/schedule/runs.ts`). One timer for the earliest armed job (`host/schedule/scheduler.ts`). A due job runs its latest due occurrence once: runs missed while the Host was down collapse into it, and an expired `at` runs once; the notice names the scheduled time and the lateness. The next occurrence is stored before the run starts. While a job's previous run runs, the new one is recorded `skipped`. A check is `bash -c <command>` through the environment's `subprocess` in the workspace (the bot's VM, as its user), within `timeoutSeconds` (default 60, at most 300): exit 0 runs the job with its standard output (its last 16 KiB), exit 1 ends the run `quiet` without the model, anything else or the time limit fails it. Runs end `ran`, `reported`, `nothing`, `quiet`, `skipped` or `failed` (`check` or `run`, with the exit code and the end of stderr). A run left `running` by a restart fails at start-up (its session is archived).
- **Failures.** A failure of a timed run reaches the Main session only when it starts a streak (`failureStreak` on the job); the run that ends a streak says so (inside its notice, or in a `recovery` notice when it has nothing else to tell). The failure notice says further failures are not told only while the job recurs and is armed.
- **Manual runs always answer** (`run`): a quiet check or a `nothing` outcome sends a short `quiet` / `nothing` notice, and every failure is told; they count in the streak like timed runs. Which notice a run's end sends is `chooseNotice` (`host/schedule/choice.ts`, pure).
- **Notices** go through the notice outbox (topic `schedule`, source `{ kind: "bot-schedule", form: "notice", summary }`; "Connectors" above), with timing `next-turn`: while the Main session runs a turn, a schedule notice waits for it to end and opens its own turn, so a `stay_silent` for it never silences the user's reply in another turn. Their text starts with `[schedule] "<name>" (<id>) — scheduled <local>, ran <local>[, late by <span>]` and a `kind:` line (`run`, `result`, `failure`, `recovery`, and for manual runs `quiet`, `nothing`).
- **Storage.** The storage domain `dsh_bot_schedules` (version 1, `host/schedule/domain.ts`): `jobs` (key: job id) and `runs` (key: run id; the latest 20 ended runs per job), written only by `host/schedule/store.ts` (design rule 42). A deleted job's runs go; a deleted bot's jobs go. At most 20 jobs per bot.
- **Not yet:** managing jobs in the Web UI.

## Managed sessions

The bot's Main session runs work in ordinary sessions of the bot (`Bot.createSession`, listed in the bot's group like any other) and operates them; the owner may also hand one of their sessions over. The spec is `docs/specs/bot-managed-sessions.md` (repository root).

- **Tools** (`plugins/sessions.ts`, row `env-bot-core-sessions` (`@1outres/dsh-bot-core/sessions`) after the schedule row, sealed like the other bot-core rows): `session_start` (`target: "bot"` or `"workspace:<id>"`, `title`, `instruction`, optional `model` and `answerer`), `session_send` (`queue` or `steer`), `session_read` (state, waiting questions, messages after a cursor), `session_answer`, `session_stop`, `session_list` (with the models `session_start` can use) and `session_release` (optionally archiving). Shown only to the Main session (`register(definition, { when })`); a call from any other session is refused. They operate only sessions the bot's Main manages (`host/managed/tools.ts`).
- **Messages of the Main** reach a managed session as user messages with source `{ kind: "bot-main-relay", form: "relay" }`, starting with `Your Main session sent a message:`.
- **Models.** `Bot.createSession(botId, { title, model })` takes `{ role: "main" }` (the default) or `{ role: "delegate", choice }`, refused (`BotSessionModelRefusal`) unless the bot's `delegates` hold the choice. In the tools a delegate is named `profile-default`, `<provider>/<model>` or `<provider>/<model>@<effort>`; omitting `model` is the main model.
- **Answerer.** Per session, `main` (the Main answers questions and plan reviews with `session_answer`; the owner can still answer in the Web UI, the first answer wins, `BotAnswerOrigin` `{ via: "main" }`) or `owner` (the Web UI only). The default is the target's (`DEFAULT_ANSWERER`: `bot` → `main`); the Main chooses at `session_start`, the owner changes it in the session's menu. Bot sessions never ask for approvals (`BOT_PERMISSION` is `never`); an approval is never the Main's to answer.
- **Notices** (topic `session`, source `bot-session`, timing `next-turn`, `host/managed/notice.ts`): every live turn end of a managed session (completed, failed, cancelled, except a turn the Main stopped itself), every question or plan review that opens (for either answerer), and the end of a management by the owner (taken back, archived). One line starting with `[session]`; the Main reads the session with `session_read`.
- **Handing over** (`botManagedSessions` Remote: `watch`, `entrust`, `release`, `setAnswerer`, the owner only): a bot session that is not its Main, a schedule run's or archived. In the Bots section a managed session's row ends in a small mark; its menu offers **Let Main manage**, then the other answerer and **Stop letting Main manage**.
- **Prompt.** The Main gets the section `bot:managed-sessions`; a session the Main started is of the kind `delegated` (its membership record says `startedBy: "main"`, written before its first turn), with its own `bot:session` text and no channel sections; every managed session gets the context `bot:management` (who operates it, who answers its questions).
- **Storage.** `dsh_bot_managed_sessions` (version 2, compatible with 1, `host/managed/domain.ts`): `sessions` keyed by session id (`botId`, `target`, `answerer`, `origin`, `label?`, `since`), written only by `host/managed/store.ts` (design rule 53), and `workspaces` (the Workspace grants, keyed `<botId>/<workspaceId>`), written only by `host/managed/grants-store.ts` (design rule 56). A deleted bot's rows go; archiving a session ends its management.
- **Workspaces** (spec §10). The owner grants a bot DSH Workspaces in the bot's settings (**Workspaces**: Agent preset other than a bot's, permission mode, model; `botWorkspaces` Remote). The Main starts ordinary DSH sessions there (`sessionController.create` under the grant's preset, then its permission and model), never recorded as the bot's, so bot-core's isolation, permission pin, working directory and prompt rows do not reach them. Omitted `model` is the grant's; only delegates may be named. The owner answers by default (DSH's own UI); with `main` bot-core takes the questions onto its board; approvals are always the owner's and are only told to the Main. Workspace operations are refused in a Main turn that took in input from anyone but the owner's side (`host/managed/authority.ts`). DSH's Workspace session rows gain **Let a bot manage** (a submenu of the granted bots), the answerer switch and **Stop letting … manage**, and a quiet mark. Revoking a grant or removing the Workspace ends the management with a notice; deleting the bot drops its grants.

## Notes

A bot's long-term memory is a folder of notes in its workspace, `notes/<UUIDv7>.md` (YAML frontmatter `title`, `type`, `aliases`, `summary`, `pinned`; links `[[<UUID>|text]]`); the spec is `docs/specs/bot-notes.md` (repository root).

- **Row** `env-bot-core-notes` (`@1outres/dsh-bot-core/notes`, `plugins/notes.ts`, after the prompt row, sealed with the revision token like the other bot-core rows; templates, overlays and environment rows cannot name it). It registers `note_read`, `note_write` (`create` / `update` with `body` or `edits` / `append`), `note_link` and `note_search` for every session of the bot, the runtime context `bot:pinned-notes` (310: the pinned notes' text, at most 4,000 characters together; Main, Web and separate schedule runs), and an `agent/pre-step` listener (design rule 50) that brings the notes up to date before every step, so DSH's `refreshContext` sends a pinned note's new text with the next request, and adds a `bot-notes` notice after an owner's message (the Web UI, or a channel message whose header marks `owner`) naming the notes it mentions (Main and Web sessions). Each call goes to the `bot` service under a symbol with the revision's token (`CALL_NOTE_TOOL`, `PREPARE_NOTES`, `PINNED_NOTES`).
- **Files** (`host/notes/`). Read and written only through the file system the calling revision's files row handed over (the bot's VM), never the Host's: new notes with `createIfAbsent`, changes with `replaceIfVersion` over the version last read. The files are the source of truth: per bot, bot-core keeps what it last read of each file and the link index built from them (titles, aliases, links, backlinks; `catalog.ts`), lists `notes/` before every use and reads again only the files whose version changed (an edit with `bash` is seen). A file that is not a valid note is left out and listed in the results. A bot's operations run one at a time.
- **The model never sees an id**: links are read and written by title (or an alias only one note has); a write naming no single note, or a pinned total over the limit, is not saved and says why; a link to a date creates that day's daily note. Nothing is linked automatically: a write's result suggests numbered links (`L1`…) for what it added (titles and aliases of at least two characters folded with NFKC and case, Latin names on word boundaries, dates written with their year), which `note_link` applies until the note is written again.
- **Initial notes** (`host/notes/initial.ts`): `Owner` (person) and `Now` (topic), pinned, placed once per bot (above, "Schedules" → initial workspace files).
- **Notes screen** (the bot session shell's **Notes** side panel, `client/notes/`, wired in `client/wiring/notes.ts`; spec §12). The `botNotes` Remote (`host/notes/panel.ts`, types `src/shared/notes.ts`) serves it, read-only and keyed by `sessionId` like `botFiles`: a session bot-core recorded as a stored bot's gets that bot's notes through its registered revision's environment fs, anything else `bot-note/not-bot-session`; `watch` (status: `ready` with a `revision`, counts, pinned characters and invalid files, or `unavailable` with the reason), `list` (newest first, by type), `search` (note_search's matching, `host/notes/search.ts`, shared with the tool), `read` (the body as stored, its link targets, Links with missing ones, Backlinks with the stored line), `month` (daily notes of a month, today in the bot's time zone). Every query lists `notes/` again; while watched, a change bot-core learns of (a note tool's write, a step's reading, `BotNotes.subscribe`) or an environment attach/detach reads them again and moves the revision, and the panel runs what it shows again.
## Skills

A bot's skills are its procedures for the kinds of work its owner repeats, one directory `skills/<name>/` of its workspace each (`SKILL.md` with frontmatter `name` and `description`, supporting files under `references/`, `templates/`, `scripts/`, `assets/`; archived ones in `skills/.archive/<name>/`); the spec is `docs/specs/bot-skills.md` (repository root). No other skill location reaches a bot: `.agents/skills`, `.dsh/skills`, the user's and the bundled skills are left out.

- **Rows.** The group isolates `skills` and holds its own `@deepseek-ai/dsh-skill` (`env-bot-core-skill`), whose only provider is bot-core's row `env-bot-core-skills` (`@1outres/dsh-bot-core/skills`, `plugins/skills.ts`, after the notes row, sealed like the other bot-core rows). The `default` template keeps `tool-skill` (the catalog, the `skill` loader and `/name`) and has no `skill-filesystem`. The row registers the provider (invalidated whenever bot-core sees the skills change), `skill_manage` (shown only in Main and Web sessions, their reviews and the bot's curation sessions; a schedule run or a subagent reads skills with `skill` only) and an `agent/pre-step` listener (design rule 50) that reads `skills/` again before each step, so a change made with `bash` reaches the catalog the step publishes. Calls go to the `bot` service under symbols with the revision's token (`SKILL_TOOL_AVAILABLE`, `CALL_SKILL_TOOL`, `PREPARE_SKILLS`, `LIST_SKILLS`, `LOAD_SKILL`, `WATCH_SKILLS`).
- **Files** (`host/skills/library.ts`). Only through the calling revision's environment file system, never the Host's; a step lists `skills/` and stats each `SKILL.md`, reading only those whose version changed. Each load through `skill` counts a use (count and time).
- **`skill_manage`** (`host/skills/manage.ts`): `list`, `view`, `create`, `patch`, `write_file`, `remove_file`, `archive` (`absorbed_into`), `restore` (a version, or the latest change undone; also an archived skill). A change is checked whole before anything is written; `patch` and replacing a supporting file need the Agent to have viewed the file as it is now; a review Agent makes one change at most, a curation Agent three; a curation archives only to merge (`absorbed_into`) and never a skill the owner keeps.
- **History** (`host/skills/store.ts`, storage domain `dsh_bot_skills` version 2: `history` with each skill's latest 20 versions of its whole directory, `usage`, `settings` (`skillReview`, `skillCurator`), `marks` (the owner's `keep`), `curation` (when the daily archive and the weekly curation last ran); written only there, design rule 54). A version records the time, the operation, the reason and the origin (`conversation` with its session, `review`, `owner`, `curator`, or `files`: what the files held when they changed outside `skill_manage`, recorded before the next change).
- **Background review** (`host/skills/review.ts`, `review-run.ts`). After 10 steps of a Main or Web session since its last review, 30 s after a turn ended with nothing happening, unless the bot's `skillReview` is off: an Agent created like DSH's fork backend creates a child (the session's completed turns as its seed, `parentSession`, `origin: "subagent"`, the same preset and route), so its system prompt and tool list are the session's and its request reuses the cached prefix; every tool but `skill_manage` is refused by a guard. It gets the review prompt once and is disposed at its turn's end; it is in no session list.
- **Curation** (`host/skills/curation.ts`, `retention.ts`, `curation-run.ts`; spec §12). Once a day per bot, active skills neither loaded nor changed for 30 days are archived (origin `curator`, reason "Unused for 30 days"), except those the owner keeps and those an armed schedule job's instruction or check names as a word; a skill with no version or use first gets an `observed` version to count from. Once a week, while `skillCurator` is on and the skills call for it (two or more, or a `SKILL.md` over 12 KiB), 30 s after the Main was last active and while it is idle, a hidden Agent of kind `curator` (no seed, `parentSession` the Main, `origin: "subagent"`, the bot's preset and `main` model) gets the curation prompt once; every tool but `skill_manage` is refused by a guard. The last times are stored, so a restart keeps counting; what cannot run now waits for the bot's next change or an hour.
- **Web UI.** The `botSkills` Remote (`host/skills/panel.ts`) and the bot settings' **Skills** section (`client/skills/`): the review and tidy-up switches, the skills with their use, their keep mark (the row's `…` menu, a switch on the skill's page) and when each is archived, the archived ones and what is not loaded; a page per skill with its history; a page per version with its changes against the version before and its content, and **Restore this version**; **Restore** for an archived skill.

## Past conversations

A bot searches its own past conversations with its owner with `conversation_search` and reads more around a match with `conversation_read`; the spec is `docs/specs/bot-session-search.md` (repository root). DSH's `dsh-tool-session-query` is not used (it treats sessions with the same working directory as one owner's).

- **Row.** `env-bot-core-conversations` (`@1outres/dsh-bot-core/conversations`, `plugins/conversations.ts`, after the skills row, sealed like the other bot-core rows) registers both tools, shown only in Main and Web sessions (and their skill reviews, whose guard runs `skill_manage` only). Calls go to the `bot` service under symbols with the revision's token (`CONVERSATION_TOOLS_AVAILABLE`, `CALL_CONVERSATION_TOOL`).
- **What is searched** (`host/conversations/`). The bot's current and former Mains and its Web sessions, archived ones included, never the calling session, schedule runs, sessions the Main started or subagents; the set comes from bot-core's records only (`sources.ts`). Only what people wrote (source `user`, channel header lines included) and the bot's replies, as appended to the log (what a compaction replaced included, what a fork inherited left out); tools are shown by name, tool results never.
- **Reading.** Logs come from DSH's `sessionQuery` (`observeSession`, without loading the session's Agent), wired only in `src/index.ts` (design rule 56); without it the tools fail. Matching is NFKC and lower case substring, newest first, with bounded excerpts and the count of matches left out.

## Main sessions

A bot keeps one Main session (its channels, notices, `main` schedule jobs, `sessions: "main"` connectors, `stay_silent` and presented files reach it), but not forever (docs/specs/bot-main-rotation.md). When the conversation pauses (no turn for `quietMinutes`) and the context is at least `minUsagePercent` full, bot-core compacts the idle Main with the bot's own `compactNow` (`env-bot-core-compaction`, placed in the template's group that isolates `compaction`); DSH's automatic mid-turn compaction stays as the safety net. A new Main takes the place of the current one, only while it is idle (no turn, nothing queued, no open question or approval): once a day after `daily.time` in the bot's time zone, before the first input (a channel message or a notice) after `longIdle.minutes` without a turn, after `compactions.count` compactions in its log, and when the owner asks (`/new` in a channel, the bot's menu or its Main session settings). The former Main is archived and listed under the bot among its other sessions, like any archived session (by its title, shown with the archived ones); its record stays the bot's, with when and why it was replaced. The new Main does not greet and gets no turn: it stays unused until its first input, and the Web UI can write into it at once ("Blank sessions"). Before every compaction and new Main, bot-core asks the Main for one **memory write-out** turn (`host/notes/flush.ts`, preparation `bot-core/memory-flush`, order 0; English prompt in `host/notes/texts.ts`, worded for a compaction or a new Main): write what it will still need and has not noted yet into its notes (a thing's own note as its current state, today's events appended to today's daily note, what is in progress in the pinned Now), check the suggested links with `note_link`, write nothing when there is nothing new, reply in one line. The turn is a `bot-main` notice whose outputs stay off the channels and that does not count as activity; it ends once the Agent left it (idle, or its next turn). A turn that does not complete, or one still running when the maintenance's time is up, gives the maintenance up (retried like any maintenance that did not happen; `/new` is refused). `memoryFlush.enabled` (on by default) turns it off; the maintenance then goes on without it. Defaults live in the dsh-bots settings (Main session), each bot can override every field, and every trigger can be turned off. Other plugins can take part too with `Bot.registerMainPreparation` (lowest `order` first); inputs that arrive meanwhile wait and reach the Main that results. Storage: `dsh_bot_mains` version 2 (reads version 1; stored defaults without `memoryFlush` get it, on, when the store opens).

## Permission and prompt

Every bot session runs under one permission, bot-core's contract `BOT_PERMISSION` (`src/shared/permission.ts`): sandbox `danger-full-access`, approval policy `never`. A bot owns its environment, so nothing it does there is confined, and nothing asks a person for approval (an approval request of a bot Agent is rejected by DSH's approval service before any answerer, bot-core's included, sees it; questions and plan reviews still reach "Interactions" below).

- **Which sessions.** Every Agent isolation classifies as a bot's (`bot` verdict): a Main, a `createSession` session, a fork, a subagent, a resumed session. bot-core sets the permission on `agent/created`, when an Agent joins its bot's preset (`agent-preset/selected`, a blank session switched back), and on load for live bot Agents. The profile's permission defaults (`dsh-permission-presets` `defaultPreset`, `dsh-user-approval` `policy`, `dsh-sandbox-policy` `mode`) never matter for a bot session.
- **How it is recorded** (`host/permission.ts`, wired in `index.ts`; design rule 38). With `dsh-permission-presets` composed, through `permissionPresets.set` with the first configured preset whose bundle is exactly the bot's (the default table's `danger-full-access`): it records that preset as the session's `permission/preset` and writes the knobs that differ with DSH's canonical setters, so the session reads that preset, never `custom`. Its own `agent/created` listener is prepended and pins the profile's default first; bot-core's is not, so bot-core's write comes after it. A preset table without the bot's bundle is refused: the bot Agent's creation is rolled back with the reason. Without `dsh-permission-presets`, bot-core writes `sandbox/mode` and `approval/policy` with `setSandboxMode` and `setApprovalPolicy` where the session's override (`sandboxPolicy` / `approval.overrideOf`) differs. Nothing is written when the session already has it, so resumes append nothing. bot-core injects `approval` and `sandboxPolicy` for this.
- **Composer.** A bot session's composer has no permission selector: bot-core empties DSH's `conversation.input.permission` seat for it (see Composer seats under Bot session shell).
- **Not enforced afterwards.** A person who switches a live bot session with `/permission` changes its approval policy until the session's next Agent creation (a resume); the sandbox mode stays full access in the environment anyway (`@1outres/dsh-bot-vm/full-access-policy`).

**Prompt.** bot-core's row `env-bot-core-prompt` (`@1outres/dsh-bot-core/prompt`, after the schedule row, sealed with the revision token like the other bot-core rows; templates, overlays and environment rows cannot name it) takes `BOT_PROMPT_EXCLUSIONS` (`src/shared/prompt.ts`) out of every bot Agent's prompt, in every template:

| Kind                  | Name                                | Provider                                                              |
| --------------------- | ----------------------------------- | --------------------------------------------------------------------- |
| system prompt section | `harness:source`, `app:web-surface` | `dsh-harness-dev-context` (the DSH checkout, the Web GUI and its HMR) |
| system prompt section | `ui:deliverable-file-references`    | `dsh-deliverable-file-references` (Web GUI file-link guidance)        |
| runtime context       | `sandbox:policy`, `approval:policy` | `dsh-sandbox-policy`, `dsh-user-approval` (fixed for bots, above)     |
| runtime context       | `harness:source`, `app:web-surface` | `dsh-harness-dev-context`                                             |

The same row adds bot-core's own prompt (the spec is `docs/specs/bot-system-prompt.md`, repository root): the sections `bot:principles` (100), `bot:environment` (4000), `bot:session` (4100), `bot:messages` (4200, Main and Web sessions; it ends with one line per registered channel's `formatHint`) `bot:workspace-files` (4300, not subagents or curations), `bot:memory` (4400, not subagents or curations: how the bot keeps its notes, `docs/specs/bot-notes.md` §8) and `bot:skills` (4500, Main and Web sessions: how the bot keeps its skills, `docs/specs/bot-skills.md` §8), the runtime context `bot:status` (300, Main and Web sessions: the bot's enabled chat channels with their state and owners, its enabled connectors with their readiness and accounts, web lookup) and the variable `{{bot_name}}`, which the `default` template's persona uses. A section's text depends only on what is fixed for a session, so the system prompt stays the same through it; what changes is in `bot:status`. On every assembly the row asks the `bot` service (under a symbol, with its revision's token: one registered during this load) about the assembling Agent (`context.agent`, which dsh-agent sets): its bot's name, its session's kind and the status (`host/prompt/facts.ts`). The kind (`host/prompt/session-kind.ts`) comes from bot-core's records, all written before the session's first turn: a skill curation (bot-core's in-memory record: kind `curator`, before its `parentSession`; it gets only `bot:principles`, `bot:environment` and `bot:session`), a background skill review (bot-core's in-memory record: it reads as the session it reviews, before its `parentSession`), a subagent (`parentSession`), the Main (the bot's `mainSessionId`; the Main's greeting is sent only after the record names it, `BotRegistryDeps.openMain`), a `separate` schedule run (a kept run's `sessionId`), a recorded session (Web: New session, a fork); an Agent that is none of them, or not verifiably the bot's, fails its assembly. **Known limit:** a schedule run's session whose run record was dropped (latest runs only) reads as a Web session once restored from the archive. Texts are `host/prompt/texts.ts`, the parts and their choice `host/prompt/sections.ts`, the status `host/prompt/status.ts`; `test/prompt-scope.test.ts` pins the assembled system prompt and context of each kind in `test/__snapshots__/prompt-scope.test.ts.snap`.

It listens to DSH's `system-prompt/assemble` waterfall (design rule 37) and filters what the rest of the chain returns. That waterfall is scope-filtered (dsh-scope): the row's context carries the scope of the preset revision it is mounted in, which every Agent bound to that revision (and its subagents) has as its scope's parent, so DSH calls the listener for those Agents' assemblies only. Other sessions, Agents of other presets and agentless assemblies are not touched; `test/prompt-scope.test.ts` mounts the row as dsh-agent-preset-registry does, with DSH's real prompt registry and scopes, and checks both sides. DSH's request admission (`refreshContext`) keeps a removed context out unless it is `required`, which none of these is. Adding the row changes every bot preset's revision once, on upgrade (build `lib/prompt.js` before DSH loads the new `lib/index.js`, as for `lib/files.js`).

## Interactions

A bot's questions (`ask_user_question`, `@deepseek-ai/dsh-tool-ask-user`, in the `default` template as in DSH's `standard` preset), approvals (`approval/request` and an `approval` question intent) and plan reviews (a `plan-review` question intent, `dsh-plan-mode`'s `exit_plan_mode`) are answered in **bot-core's own card** in the bot session's composer seat and, for the Main session, in every connected channel that declares the kind. The first answer from anywhere wins; every other presentation then closes with who answered (the Web UI, or which channel) and what, or that it was withdrawn.

- **Joining DSH's waterfalls** (`host/interactions/answerers.ts`, wired in `index.ts`; design rule 36). bot-core listens to `user-questions/request` and `approval/request` with `prepend`, ahead of DSH's Remote Events forwarder, so DSH's Web cards (`dsh-client-ui-user-questions`, `dsh-client-ui-approval`) never get a bot's request. A question of a bot's root session (DSH itself refuses subagents' questions, `DELEGATED_CALLER`) and an approval of a bot session's Agent or of its subagents (shown in the root session, marked as a subagent's, only when the live parent chain proves the bot) are claimed without `next()`; every other Agent's request goes straight to `next()`. Unloading bot-core (or DSH's `userQuestions` going away, for questions) hands every waiting request to `next()`, as DSH's Web card delegates on teardown.
- **What DSH receives** is what its Web cards produce: the answer batch (`{ id, selected, custom? }` per question; a single-select question takes a choice or text, never both; no choice and no text skips), an approval's `allowed-once` / `rejected` (the `approval/asked` / `approval/decided` audit pair is written by DSH's approval service, as for the Web UI), an approval intent's option label (`always` only when the asker offered one, e.g. computer use's "Always allow"), a plan's approve label. A plan sent back carries the feedback as `custom`; without feedback it is DSH's `ASK_CANCELLED`, as the Web card's "discuss" sends it (`exit_plan_mode` then ends the turn, so the person writes in their own message). A plan review is presented as one when DSH's Web card would (one question, its plan as detail, the approve option and at most one other, no multi-select); otherwise as a question. An aborted request (a stopped turn) withdraws the interaction and rejects with the abort.
- **Timed questions** (`askTimed`, the tool's `mode: timed`). bot-core claims the foreground wait with `userQuestions.attachWait` as a Web card does and then owns the countdown (`counting`, the Host's deadline); a person starting to answer (a choice, text, a modal, "Take time") holds it indefinitely (`held`), as the Web card's first edit does. At the deadline bot-core rejects with `ASK_TIMED_OUT`, so DSH returns pending and the bot goes on; the interaction stays open as `continued`, and only then joins the continued calls (a call answered in time leaves nothing behind). Settling releases the claim (`return()` on the stream). Continued calls follow DSH's `userQuestions` projection of each live bot root session (`host/interactions/continued.ts`): they are answered by `userQuestions.answer` (a late reply steered into the Agent, which is resumed first), withdrawn once the projection drops them, and opened again when a queued reply is discarded. A session's continued calls appear once its Agent is live.
- **The board** (`host/interactions/board.ts`) is the one record: per session, in opening order, with the latest 8 closures of each of the 64 sessions closed in most recently; the Main session's interactions are published to the bot's channels. Ids are 10 characters.
- **The browser** (`client/interactions/`, wired in `client/wiring/interactions.ts`) follows the shown bot session through the `botInteractions` Remote (`watch(sessionId)`, `answer`, `hold`; bot sessions only) and publishes a carrier in DSH's pending-interaction registry (`ctx.uiSession.registerPendingInteraction`, precedence 10, above DSH's questions 1–2 and approvals 0), which bot-core's `conversation.composer` chain entry (at `BOT_SESSION_PRIORITY`, ahead of any other plugin's composer entry) elects: the card takes the composer seat as DSH's cards do, in DSH's QuestionComposer measures (its width axis, no border, radius-xl, input-major fill, panel elevation, eyebrow over a 16 px title, at most `min(60vh, 520px)`) with a minimise button that folds it to its header, and a stock card DSH builds from the projection for a bot session (a continued question) never wins the seat. The card: a question batch with a pager, choices, a text answer, Skip, Back/Next/Submit and the wait line ("Take time"); an approval with Reject, Allow once (or the asker's wording) and Always allow when offered; a plan rendered as Markdown with optional feedback, Request changes and Approve. A closure this page did not answer itself shows who answered and what, until closed.
- **Not supported:** questions of agentless callers (left to DSH's other answerers); the stock card's per-browser focus pause and draft persistence across reloads; `session.wait`'s `pendingInput` (it reads the Gateway's forwarded events) does not list bot-core's requests.

## Isolation

`createSession` is the intended way into a bot, but DSH itself does not prevent choosing a bot's preset elsewhere: bot presets are on the Agent preset roster, and a blank session can switch presets. bot-core hides its bots' presets in Settings (by exact id) and in the composer's preset menu (by the description every bot preset carries, since that menu has no preset id); the "Custom" heading in Settings stays, because it also holds the Creator entry. And it enforces one invariant on every Agent, at creation and whenever tools or presets change:

**An Agent of a bot's session runs that bot's preset, and an Agent on a bot's preset belongs to a session of that bot.**

Every bot session runs in the same directory path, so a session belongs to a bot by identity, not by directory:

- A **subagent** whose parent Agent is running takes its parent's classification and nothing else. Its own header proves nothing: DSH writes the preset the subagent selected there, so a Workspace Agent delegating under `bot-<id>` is not the bot's session (on the bot's preset it is locked down, below), and a bot's subagent stays that bot's whatever preset it named.
- A **subagent whose parent is not running** (a resumed child) cannot be checked: it is the bot's only if bot-core recorded the session as the bot's. Otherwise, when its header names a bot's preset, it is _unverified_ and fails closed: locked down, its working directory neither checked (on the Host or in the VM) nor changeable. A header naming no bot preset makes it no bot's (on a bot preset it is locked down too).
- **Any other session** (a Main, `createSession`, a fork): the session header's `agentPreset` (fixed at creation, inherited by forks) names the bot's preset `bot-<id>`; otherwise bot-core recorded the session as the bot's (a legacy Main, a fork it recorded on creation).
